# 26. L21302 AI技術系統集成與部署（60 分鐘）

> **本科實測命中率最高的知識點（42%）**，但官方指引篇幅只有 7,753 字（倒數第二少）——
> 投報率最高的一節，不要因為它篇幅短就輕忽。
> 初級的「模型監控與維護」只教到「要監控」，中級要求你**設計架構、選部署模式、判讀指標**。

## 學習目標
- 掌握系統集成的五個面向，能判斷「整合失敗」題型的癥結在哪一層
- 分辨四種部署模式的適用情境與各自的挑戰
- 精準區辨延遲、吞吐量、可用率三個效能指標（中文關鍵詞掃描達 18 題）
- 分辨資料漂移與概念漂移，並知道對應的偵測與處置流程

## 26.1 系統集成的五個面向

AI 系統不是獨立模組，要與企業既有資訊架構**無縫整合**。

| 面向 | 整合什麼 | 常考點 |
|---|---|---|
| **資料來源與資料管線** | 資料倉儲、資料湖、IoT 感測、第三方 API | 資料管線涵蓋擷取→轉換→清理→入庫 |
| **企業內部系統** | ERP、CRM、POS、MES | **模型輸出要回寫到既有系統才有價值** |
| **API 與平台接軌** | RESTful API、gRPC、Webhooks | 要納入容錯、快取、負載管理 |
| **安全與權限控管** | OAuth2／JWT 驗證、角色權限、API Gateway | 只有部分用戶可重訓或調參 |
| **跨雲與異質系統** | 本地訓練 + 邊緣／雲端推論 | 用中介整合層或 Service Mesh 避免資訊孤島 |

> **考點提醒**：「模型準確率很高但沒人用」這類情境題，癥結多半在
> **第二層（沒有整合回 ERP/CRM 等日常作業流程）**，不是模型不夠好。

### 資料倉儲 vs 資料湖

| | 資料倉儲（Data Warehouse） | 資料湖（Data Lake） |
|---|---|---|
| 資料型態 | 結構化為主 | 大規模**非結構化**資料 |
| 寫入時機 | Schema-on-Write（先定義結構） | Schema-on-Read（先存再說） |
| 典型用途 | BI 報表、固定分析 | 原始資料保存、探索式分析、模型訓練 |

## 26.2 系統架構設計

### 四種架構手段

| 手段 | 做什麼 | 優點 | 挑戰 |
|---|---|---|---|
| **微服務** | 拆成一組小型服務，各自獨立部署 | 錯誤隔離、跨團隊並行開發、可依模組彈性擴充 | 介接需標準 API、分散式管理複雜 |
| **容器化（Docker）** | 把應用與依賴環境封裝在一起 | **跨平台部署一致性**（官方原文考點） | 需搭配編排工具管理 |
| **容器編排（K8s）** | 資源調度、故障恢復 | 滾動更新、自動擴縮、負載平衡 | 學習曲線陡 |
| **模型服務化** | 封裝成 HTTP/REST 推論服務 | 多版本管理、API 安全、記錄與監控 | 需設計版本切換策略 |

> **容器技術的主要優點是什麼？** 官方正解：**促進模型跨平台部署與環境一致性**。
> 誘答會寫「加快模型推論速度」「提升模型準確率」—— 容器解決的是**環境問題**，不是效能或精度。

### 高可用性設計

```
冗餘部署（Redundancy）── 多節點，避免單點故障
容錯切換（Failover）──── 節點故障自動切到備援
負載平衡（Load Balancing）── 多推論節點分擔請求
自動擴縮（Autoscaling）── 依流量調整容器數量
```

## 26.3 四種部署模式

| 模式 | 優勢 | 適用情境 | 挑戰 |
|---|---|---|---|
| **公有雲** | 彈性擴充、部署快、按量付費、全球節點 | 新創、跨地區、GPU 密集訓練 | 法規遵循、**資料主權**、供應商鎖定 |
| **私有雲／地端** | 資安可控、**資料不外流**、可依產業法規客製 | **政府、金融、醫療** | 建置與維運成本高、擴展性受限 |
| **邊緣運算** | **即時反應、降低延遲、提升隱私** | 工業設備監控、智慧城市、車聯網 | 運算資源有限、更新同步需另外設計 |
| **混合部署** | 兼顧算力、速度與資料保護 | 雲端訓練 + 邊緣推論 | 整合難度高，需同步與一致性機制 |

**判準口訣**：

```
講到「資料隱私、本地控制、法規嚴格」 → 私有雲／地端
講到「低延遲、離線可用、頻寬有限」   → 邊緣運算
講到「快速試驗、彈性擴充、GPU 需求」 → 公有雲
講到「訓練在雲端、推論在現場」       → 混合部署
```

> 官方考過：「在邊緣運算架構中，AI 模型的推論通常會發生在哪裡？」
> 正解：**終端裝置本地端**。

### 發布策略（控制上線風險）

| 策略 | 作法 | 何時用 |
|---|---|---|
| **藍綠部署** | 兩套環境並存，**一次性切換** | 需要能快速整批回滾 |
| **金絲雀發布** | 先導流極小比例，**逐步放大** | 風險高、要邊觀察邊放量 |
| **滾動更新** | 分批替換容器版本，**不中斷服務** | 例行版本更新 |
| **A/B 測試** | 兩版本同時服務不同群體 | 要比較業務成效 |
| **影子模式** | 新模型只推論、不影響決策 | 上線前最後驗證 |

## 26.4 效能三指標（中文關鍵詞掃描達 18 題）

```
延遲（Latency）      單次請求從輸入到回覆的時間 ──── 使用者感受到的「卡頓」
吞吐量（Throughput） 單位時間能處理的請求數 ────── 系統的「容量」
服務可用率（Uptime） 長時間運行不中斷的比例 ────── 穩定性
```

| 症狀描述 | 該測 / 該優化 |
|---|---|
| 「使用者反映互動過程卡頓，已排除網路與前端問題」 | **延遲** |
| 「尖峰時段大量請求排隊、部分請求逾時」 | **吞吐量**（擴增節點、批次化） |
| 「系統偶發中斷、單一節點故障導致全掛」 | **可用率**（冗餘、容錯切換） |
| 「GPU 記憶體吃滿」 | 資源使用率（系統層級指標） |

> **這三個最容易混答**。判準是問題描述的主體：
> 單次請求的**時間**＝延遲；單位時間的**數量**＝吞吐量；長時間的**不中斷**＝可用率。

### 三個指標的權衡關係

```
             ┌──────────────┐
   批次大小 ↑ │  吞吐量 ↑     │  同一批處理更多請求，單位時間產出增加
             │  延遲   ↑     │  但每個請求要等整批湊滿才被處理
             └──────────────┘

             ┌──────────────┐
   節點數量 ↑ │  吞吐量 ↑     │  多節點分擔請求
             │  可用率 ↑     │  單點故障不致全掛
             │  成本   ↑     │  代價是資源費用
             └──────────────┘

             ┌──────────────┐
   模型壓縮   │  延遲   ↓     │  量化、蒸餾讓推論變快
   （量化/蒸餾）│  準確率 ↓     │  代價是精度略降
             └──────────────┘
```

> **這組權衡是情境題的核心**：題目會給一個限制（例如「必須在 100ms 內回應」），
> 要你選出正確的手段。記住「**批次化換吞吐量、壓縮換延遲、多節點換可用率**」，
> 每一項都有代價。

### 三層 KPI（官方明示的分層）

| 層級 | 指標 |
|---|---|
| 系統層級 | 推論延遲、吞吐量、服務可用率、資源使用率（GPU 記憶體） |
| 應用層級 | 推薦點擊率（CTR）、準確率、F1-Score、異常偵測精確度 |
| 業務層級 | 轉換率提升、成本節省、客戶留存率、ROI |

> 官方建議採「**技術指標 + 業務指標雙軌制**」，讓工程與業務有共同語言。
> 這正是「離線 AUC 很漂亮但 CTR 反而下降」那類題目的判準來源。

## 26.5 MLOps 與持續維運

**MLOps 是 DevOps 在 AI 領域的延伸**，把訓練、測試、部署、監控做持續整合與自動化。

> 官方考過：「MLOps 的主要目的為何？」
> 正解：**實現 AI 模型的自動化開發、部署與持續維運流程**。
> 誘答會寫「提升模型準確率」—— MLOps 管的是**流程**，不是精度。

### CI/CD 在 AI 的樣貌

| 階段 | 內容 |
|---|---|
| CI 持續整合 | 原始碼或**資料**變動即觸發訓練與測試；整合單元測試、準確率驗證、效能基準比較 |
| CD 持續部署 | 通過門檻的模型自動部署到測試／生產；支援 A/B 測試或藍綠部署控制風險 |
| 模型版本控管 | MLflow（實驗記錄、訓練、部署、版本）、DVC（資料集與模型的版本追蹤） |

> **AI 的 CI 與一般軟體不同的地方**：觸發條件不只程式碼，**資料變動也要觸發**；
> 測試不只單元測試，還要驗證模型準確率與效能基準。

### 監控與回饋

```
偵測 ──→ 觸發 ──→ 處置
 │        │        │
 │        │        └─ 再訓練 Pipeline／熱更新（Hot Swap）／滾動更新
 │        └─ 設定門檻（例如準確率下降 5%）
 └─ 模型漂移、資料漂移、錯誤率、延遲、吞吐量
```

可視化與預警：Prometheus + Grafana 整合 Log 分析與 Dashboard，異常時自動通知工程人員。

### 回收週期（官方給的節奏）

| 頻率 | 做什麼 |
|---|---|
| 每日 | 監控推論效能與使用情況 |
| 每週 | 收集錯誤樣本與業務回饋 |
| 每月 | 模型重新評估或確認 retraining 需求 |

## 26.6 兩種漂移（高頻考點，7 題）

| 類型 | 定義 | 判準 | 典型情境 |
|---|---|---|---|
| **資料漂移（Data Drift）** | 輸入資料的統計特徵改變 | 變的是 **X 的分布** | 新客群湧入、感測器換型號、欄位分佈改變 |
| **概念漂移（Concept Drift）** | 輸入與輸出的關係改變 | 變的是 **X → Y 的映射** | 疫情改變消費行為、詐騙手法演化 |
| 模型漂移（Model Drift） | 模型**預測分佈**與訓練時期不同 | 是前兩者造成的結果 | 預測值整體偏移 |

一句話判準：**變的是輸入分布，還是輸入與輸出的關係。**

偵測方法：KS 檢定、KL 散度、**PSI（Population Stability Index）**。

> 官方考過：「持續監控部署後 AI 模型效能的主要目的為何？」
> 正解：**偵測模型概念漂移與效能下降**。

### 處置流程

漂移超過門檻 → 自動觸發再訓練 → 更新資料集與標註品質 → 版本控管後滾動釋出。
變化快速的場景可搭配 **AutoML 或線上學習（Online Learning）** 做持續微調。

### 從症狀反推病因（情境題的解法）

| 觀察到的現象 | 最可能的成因 | 該做什麼 |
|---|---|---|
| 輸入欄位分佈明顯改變，但模型邏輯仍成立 | **資料漂移** | 用新分佈資料再訓練 |
| 輸入分佈沒變，但預測準確率持續下滑 | **概念漂移**（X→Y 關係變了） | 重新定義標籤、重新訓練 |
| 訓練時表現好、上線後立刻就差 | **訓練／服務偏差**（前處理不一致） | 檢查線上線下的特徵管線是否相同 |
| 整體指標正常，但某個客群表現特別差 | 分群效能落差 | **分群監控**，不要只看整體平均 |
| 尖峰時段準確率不變但逾時率上升 | 容量問題，不是模型問題 | 擴增節點／批次調整 |

> **最容易誤判的一格是第三列**：訓練好、上線差，很多人第一反應是「模型過擬合」，
> 但如果離線驗證分數也很好，那更可能是**線上與離線的特徵處理不一致**
> （Training-Serving Skew），要去比對兩邊的前處理程式碼，不是重訓模型。

## 26.7 跨部門整合

模型上線不是資訊部門一個人的事，官方明列四個角色的責任：

| 部門 | 職責 |
|---|---|
| 業務與行銷 | 提供需求情境與績效指標，依模型輸出調整策略並回饋 |
| 客服與營運 | 回收實際互動案例與異常反應，供持續優化 |
| 法務與風險 | 審查資料隱私、模型公平性、風險揭露，建立合規使用框架 |
| 資訊部門 | 部署、權限管理、API 整合與維運支援 |

> 官方考過：「為確保模型可與業務流程無縫對接，通常需要哪種角色？」
> 正解：**產品經理與工程人員**。

## 26.8 官方考過什麼

| 考點 | 怎麼問 | 正解思路 |
|---|---|---|
| 容器技術 | 使用 Docker 的主要優點 | **促進跨平台部署與環境一致性**（不是加速推論） |
| MLOps | MLOps 的主要目的 | **自動化開發、部署與持續維運流程** |
| 邊緣運算 | 推論發生在哪裡 | **終端裝置本地端** |
| 持續監控 | 監控的主要目的 | **偵測概念漂移與效能下降** |
| 跨部門 | 無縫對接需要哪種角色 | **產品經理與工程人員** |
| 效能指標 | 「互動卡頓、已排除網路與前端」要測什麼 | **延遲**（不是吞吐量、不是長時間穩定度） |
| 漂移辨識 | 資料分佈長期改變 vs 輸入輸出關係改變 | X 的分布 → 資料漂移；X→Y 的關係 → 概念漂移 |
| 部署模式 | 資料隱私與本地控制需求 | **地端私有部署** |
| 成效追蹤 | 離線 AUC 好但 CTR 下滑、成本上升 | **只看離線指標、忽略線上業務指標與成本** |

## 26.9 易錯與陷阱

- [ ] 容器的優點是**環境一致性與跨平台**，不是加速推論或提升準確率
- [ ] MLOps 管的是**流程自動化**，不是提升模型精度
- [ ] 邊緣推論發生在**終端裝置本地端**，不是雲端或閘道器
- [ ] **延遲**是單次請求的時間、**吞吐量**是單位時間的數量，兩者不同
- [ ] 可用率是「不中斷的比例」，與延遲、吞吐量是三個面向
- [ ] 資料漂移看 **X 的分布**；概念漂移看 **X→Y 的關係**
- [ ] 模型漂移是**結果**，資料／概念漂移才是成因
- [ ] 金絲雀＝**逐步放大流量**；藍綠＝**一次性切換**；滾動＝分批替換
- [ ] 影子模式**只推論不影響決策**，不是分流給部分使用者
- [ ] 私有雲的優勢是**資料不外流**，代價是成本高與擴展性受限
- [ ] AI 的 CI 要由**資料變動**觸發，不是只看程式碼
- [ ] 模型輸出**要回寫到 ERP／CRM** 才產生業務價值
- [ ] 資料倉儲是結構化 Schema-on-Write；資料湖是非結構化 Schema-on-Read
- [ ] 離線指標好**不等於**導入成功，要看業務層級 KPI 與成本
- [ ] 再訓練是由**漂移門檻觸發**，不是固定每月重訓就好
