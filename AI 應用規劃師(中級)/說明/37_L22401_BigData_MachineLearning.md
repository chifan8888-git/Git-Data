> 一句話定位：科目 3（L23）問的是「這個演算法怎麼運作」，L22401 問的是「當資料變成 TB 至 PB 級、而且還一直流進來，這個演算法該怎麼被餵、被訓、被評估、被重訓」。初級只要求你會分辨監督式與非監督式；這裡要求你能在單機前提失效之後，仍然設計得出一條跑得動的機器學習流程。

## 37.1 被打破的三個前提

傳統機器學習流程建立在三個沒說出口的假設上。大數據環境逐一把它們打掉，才有了這個知識點。

| 舊前提 | 大數據環境的現實 | 直接後果 |
|---|---|---|
| **完整樣本**：資料可一次備齊、靜態不動 | 資料持續產生，訓練當下只看得到某個時間切片 | 需抽樣策略、增量學習、漂移監控 |
| **記憶體內計算**：資料塞得進 RAM | 單檔就可能 50GB 以上，遠超可用記憶體 | 需分批載入、欄式格式、分散式聚合 |
| **單機環境**：一台機器跑到收斂 | 模型與資料量都超過單機上限 | 需分散式訓練、檢查點（Checkpointing）、容錯 |

### 五大特性 → 對機器學習流程的衝擊

| 特性 | 卡住的環節 | 主要對策 |
|---|---|---|
| **Volume**（量大） | 資料載入、訓練時間、指標計算 | 分批載入（Mini-Batch Loading）、抽樣、HDFS／Parquet、Spark MLlib、串流式指標 |
| **Variety**（型態多） | 特徵工程、資料整合 | 多模態編碼（Word2Vec／BERT、CNN、Spectrogram）、資料湖、對齊與融合 |
| **Veracity**（來源異質、可信度不一） | 前處理、可追溯性 | Schema Mapping、資料編目（Data Catalog）、資料來源追蹤（Data Lineage）、版本控制 |
| **Velocity**（流動快） | 模型更新、上線服務 | 串流處理、增量學習、近即時更新、模型輪換 |
| **Value**（價值密度低） | 訓練效率、過擬合 | 特徵選擇（Lasso）、降維（PCA）、高資訊密度抽樣、主動學習（Active Learning） |

> 考試判讀訣竅：題幹出現「毫秒級」「即時」就往 Velocity 走；出現「文字＋影像＋表格」就往 Variety 走；出現「上億筆」「50GB」「PB 級」就往 Volume 走；出現「來源眾多、格式不一、要能追溯」就往 Veracity 走。

### Variety 的文字模態：順序資訊要靠位置編碼補進去

上表的 Variety 一列提到用 BERT 這類 Transformer 模型把文字轉成向量。這裡有一個在文本分類專案實際會踩到的細節：**自注意力（Self-Attention）本身不帶順序資訊**。

```
自注意力對輸入序列是「排列不變（Permutation Invariant）」的
   ↓
把「貓追狗」的 token 打亂成「狗追貓」
   ↓
若沒有另外提供位置資訊，兩者算出來的表示會是相同的
   ↓
模型對語序不敏感 → 語意判斷出錯
```

補救機制是**位置編碼（Positional Encoding）**：在每個詞嵌入（Embedding）向量上**加上該位置對應的位置向量**，讓同一個詞出現在不同位置時得到不同表示，模型才分得出先後與相對距離。所以當文本分類模型出現「對詞序變化不敏感」的症狀時，第一個該回頭檢查的就是位置編碼有沒有被正確加入、或是否在某一層被覆蓋掉。

**四個貼在一起、最容易互相張冠李戴的元件：**

| 元件 | 負責什麼 | 不負責什麼 |
|---|---|---|
| **位置編碼（Positional Encoding）** | 提供序列中的**先後位置**資訊 | 不提供章節、段落或文件結構的語意；也不是隨機擾動——位置資訊必須確定且可重現 |
| **注意力遮罩（Attention Mask）** | 屏蔽 padding 位置、或在解碼時擋住尚未生成的詞 | 不提供位置資訊 |
| **詞嵌入（Embedding）** | 把 token 映射成語意向量 | 同一個詞在任何位置都對到同一個向量，本身分不出順序 |
| **平行化運算** | 整個序列一次算完，是 Transformer 相對 RNN 逐步遞迴的速度來源 | 正因為放棄了逐步遞迴，才**必須**額外補上位置資訊 |

位置編碼只解決「順序」這一件事。若需求是讓模型理解長文件的章節層次，要靠文件切塊策略、階層式模型或結構化標記來處理，不是把位置編碼調大。Transformer 完整架構屬於科目 1（L21101）的範圍，這裡只需掌握「大數據文字模態進 Transformer 時，順序資訊從哪裡來」。

## 37.2 Volume：資料量與模型效能的關係

### 加資料到底有沒有用

| 情境 | 再加資料的邊際效益 | 該做的事 |
|---|---|---|
| 訓練差、測試也差（高偏差／欠擬合） | 通常很低 | 提高模型容量、補特徵 |
| 訓練好、測試差（高變異／過擬合） | 通常較高 | 擴充資料來源與多樣性、正規化 |
| 標註本身大量錯誤 | 可能是負的 | 先清洗標註，再談加量 |
| 新資料與舊資料同分佈且重複性高 | 遞減得很快 | 改做高資訊密度抽樣／主動學習 |

效能曲線會隨資料量增加而趨緩，最終被模型容量與資料本身的雜訊上限擋住。高容量模型（深度網路）通常能吃下更多資料才飽和，低容量模型（線性迴歸）較早就到頂——這是「為什麼大數據時代深度學習受益最大」的實際理由。

**關鍵對比**：樣本數多 ≠ 資料品質好。官方指引把這句話單獨列成一段，考題也照著考（見 37.4）。

### 資料塞不進記憶體怎麼辦

```
單機 RAM 撐不住
 ├─ 分批載入（chunk / mini-batch）……… pd.read_csv(..., chunksize=10000)
 │                                      回傳可迭代的 TextFileReader，逐批處理後釋放
 ├─ 降型別（dtype=int32 / category）… 只能等比例縮減，救不了數量級差距
 ├─ 抽樣（Sampling）………………………… 換得速度，代價是代表性風險
 └─ 換架構（Spark / Ray / Dask）……… 資料留在叢集，把運算推到資料所在之處
```

| 儲存與格式 | 特點 |
|---|---|
| **HDFS** | 分散式檔案系統，提供水平擴展與副本容錯 |
| **Parquet** | 欄式（Columnar，按 column 存放；官方指引譯為「列式」）壓縮格式，只讀需要的欄位，大幅降低 I/O |
| **TFRecord** | 序列化的訓練樣本格式，搭配 `tf.data` 做預取與快取 |
| **Delta Lake / Apache Iceberg** | 在資料湖上加版本控制、Schema 演進與交易語意 |

### 抽樣 vs 全量

| 維度 | 抽樣（Sampling） | 全量（Full Scan） |
|---|---|---|
| 成本 | 低 | 高 |
| 少數類／長尾事件 | 容易被抽掉 | 保留完整 |
| 適用 | 探索性分析、超參數初篩 | 最終模型訓練、稀有事件偵測 |
| 折衷做法 | 分層抽樣（Stratified Sampling）保住類別比例；近似演算法（t-digest、GK）在誤差容忍內換效率 | — |

### 分散式環境下的統計與評估

單機寫法搬到叢集會直接爆掉。正確模式是**各節點先算局部統計量，再彙總**：

```python
# 錯：把 10 億筆拉回 Driver 單機記憶體，必然 OOM，也放棄了平行能力
data = df.collect()

# 對：由各 Executor 在自己的分區算局部量（count / sum / sum of squares），
#     只 shuffle 極小的中間結果再合併成全域標準差
df.agg({'col': 'stddev'})
```

同理，評估指標也要改成可分批累積的形式：**Streaming Confusion Matrix**（逐批累加 TP／FP／FN／TN）與**滑動窗口式 AUC（Streaming AUC）**，取代一次性把全部預測收齊再算的靜態做法。

## 37.3 分散式訓練與訓練效能最佳化

### 三種並行模式

| 模式 | 切的是什麼 | 每個節點放什麼 | 適用情境 |
|---|---|---|---|
| **資料並行（Data Parallelism）** | 切**資料** | 完整的模型**副本** | 樣本量大、模型中等（影像分類、一般 NLP） |
| **模型並行（Model Parallelism）** | 切**模型** | 模型的**一部分** | 單機記憶體放不下整個模型（GPT、BERT 等超大模型） |
| **混合式並行（Hybrid Parallelism）** | 兩者都切 | 模型分片 × 多份資料 | 同時要橫向擴展與放大模型 |

資料並行每輪訓練後需做**梯度彙總（Gradient Aggregation）**再更新全域參數；常見實作為 Horovod、TensorFlow MultiWorkerMirroredStrategy。

### 四類最佳化手段各自解決什麼瓶頸

| 手段 | 解決的瓶頸 | 機制 | 副作用／限制 |
|---|---|---|---|
| **GPU／TPU 硬體加速** | 運算量 | 張量與大矩陣平行運算 | 成本、資源排程 |
| **混合精度（Mixed Precision）** | 記憶體 + 運算 | FP32 與 FP16 並用 | 需注意數值下溢，通常配合 loss scaling |
| **梯度累積（Gradient Accumulation）** | 記憶體 | 多個小 batch 先累積梯度，再一次更新參數 | 更新頻率下降，單輪 wall-clock 未必變快 |
| **梯度壓縮／延遲同步** | **網路傳輸** | Top-k 稀疏化、量化、Delayed Gradient | 壓縮過度會影響收斂品質 |

### 批次大小與泛化

在其他條件不變（尤其學習率未同步調整）時，官方考過的觀察是：

```
Batch Size 小（如 32）
  → 梯度估計雜訊大 → 像一種隱含正則化 → 較易走到平坦解 → 泛化通常較好，但訓練較慢

Batch Size 大（如 4096）
  → 梯度估計穩定、硬體利用率高 → 訓練較快
  → 但缺乏隨機擾動，較易停在尖銳的局部極小值附近 → 泛化可能變差
```

注意這是**在其他超參數不變的前提下**的現象，不是「大批次必然更差」；實務上大批次通常需要搭配學習率調整（如 linear scaling、warmup）才能補回來。

### 訓練中斷與早停

- **Checkpointing**：定期存下權重與訓練狀態，解決的是「訓練被中斷後能接續」與容錯，跟過擬合無關。
- **Early Stopping**：監控**驗證集**指標，在不再持續改善時停止，解決的是過度訓練與資源浪費。

## 37.4 資料品質與偏態：大量不等於高品質

### 四種常見病灶

| 問題 | 對模型的影響 | 對策 |
|---|---|---|
| 類別不平衡（Class Imbalance） | 過度學習主流類別，少數類系統性漏判 | 類別加權、重抽樣、成本敏感學習 |
| 標註錯誤（Label Noise） | 模型硬記雜訊標籤，訓練／驗證落差擴大 | 清洗標註、弱標註＋人工複核、主動學習 |
| 冗餘與重複樣本 | 有效樣本數被高估，助長過擬合 | 去重、資訊增益導向抽樣 |
| 感測器漂移、系統性偏移 | 特徵分佈隨時間偏移，模型逐步失準 | 滾動中位數校正、加入缺失指標特徵 |

### 不平衡資料的處置對照

| 方法 | 做法 | 主要風險 |
|---|---|---|
| **隨機過採樣（Random Oversampling）** | 複製少數類樣本 | 樣本完全相同，**最常造成過擬合** |
| **隨機欠採樣（Random Undersampling）** | 刪除多數類樣本 | 丟失多數類資訊，資料本就稀少時更不可取 |
| **SMOTE** | 在少數類樣本與其近鄰間**內插**生成合成樣本 | 多樣性優於複製，但合成點可能落在類別邊界 |
| **類別加權 / 成本敏感學習** | 在**損失函數**中放大少數類誤判的懲罰 | 不改變資料，需調權重比例 |
| **調整決策門檻（Threshold）** | 事後移動判定閾值提升召回率 | 未改變資料不平衡的根本，提升有限 |

### 評估指標必須跟著換

| 指標 | 在極度不平衡下的表現 |
|---|---|
| **Accuracy** | 失去判別力。0.5% 詐欺率時，永遠猜「正常」就有 99.5% 準確率、詐欺召回率為 0% |
| **Precision 單看** | 可被「幾乎不發警報」的保守模型灌高，反而漏抓更多 |
| **Recall / F1** | 反映漏判風險，通常是風控、醫療情境的主軸 |
| **ROC-AUC** | X 軸 FPR、Y 軸 TPR。在極少數正例下容易偏樂觀 |
| **PR-AUC** | X 軸 **Recall**、Y 軸 **Precision**。對少數類更敏感，極度不平衡時優先 |
| **Balanced Accuracy / Macro AUC** | 讓各類別權重相等，避免被主類別主導 |

### 順序問題：重抽樣與特徵篩選一定在切分之後

```
錯：全體資料 → SMOTE / 特徵篩選 / 標準化 → 訓練／測試切分 → 評估
    測試集資訊滲入建模流程 → 資料洩漏（Data Leakage）→ 分數虛高

對：訓練／測試切分 → 只在訓練折上 fit（SMOTE、篩選、標準化）
    → 以同一組參數 transform 測試折 → 評估
```

同一份資料若有群組結構（同一位病患、同一間門市、同一名使用者的多筆紀錄），還要再加一層：用 **Group K-Fold** 讓同一群組不會同時出現在訓練與測試集；類別不平衡則用 **Stratified K-Fold** 維持每折的類別比例。

## 37.5 Velocity：批次訓練 vs 線上學習

### 三種訓練節奏

| 維度 | 批次訓練（Batch） | 微批次／近即時 | 線上／增量學習（Online / Incremental） |
|---|---|---|---|
| 資料取用 | 全量重讀 | 小區段切片 | 單筆或極小批到達即更新 |
| 更新頻率 | 天／週 | 分鐘 | 秒以下 |
| 典型演算法 | 任意 | Fine-tuning、部分重訓 | SGDClassifier、Perceptron、Naïve Bayes、River、Vowpal Wabbit |
| 主要風險 | 對分佈變化反應慢 | 排程與資源競爭 | **災難性遺忘（Catastrophic Forgetting）**、被雜訊樣本帶偏 |

### 串流基礎設施與服務模式

```
資料來源（IoT / Web Log / 交易）
   │
   ├─ 邊緣運算節點 ─────── 就近處理，壓低延遲
   │
   ├─ 訊息佇列（Kafka / Kinesis / Pub-Sub / Event Hub）
   │
   ├─ 串流處理（Flink：低延遲；Spark Streaming：高容錯）
   │        └─ 窗口計算、狀態管理、複雜事件處理（CEP）
   │
   └─ 雲端資料湖 ───────── 保全量，供後續訓練與回溯分析
```

上面這種「即時路徑顧時效、批次路徑保全量」的分工，是 IoT 情境題最常見的正解骨架。服務端則有三種型態：

| 部署模式 | 觸發方式 | 典型用途 |
|---|---|---|
| **Batch Serving** | 排程 | 每日風險預測報表 |
| **Online / API Serving** | 請求驅動（REST／gRPC） | 即時查詢、線上推薦 |
| **Streaming Inference** | 事件驅動（Kafka／Flink） | 低延遲異常偵測 |

### 兩種漂移別混淆

| 名稱 | 變的是什麼 | 例子 | 偵測 |
|---|---|---|---|
| **資料漂移（Data Drift）** | 輸入特徵的分佈 P(X) | 消費行為隨季節改變 | KS 檢定、KL 散度、PSI |
| **概念漂移（Concept Drift）** | 特徵與標籤的關聯 P(y\|X) | 詐騙手法整個換了一套 | 需標籤回流後看效能衰退 |

避免頻繁全模型重訓的做法：動態模型選擇（Model Switching）、模型輪換（Model Rolling），搭配 A/B 測試或 Canary Release 分批導流，把新版本風險控制在小比例流量內。

## 37.6 資料管線、特徵存放與端對端流程

```
┌──────────┐   ┌──────────┐   ┌──────────┐   ┌──────────┐   ┌──────────┐
│ 資料整合  │→ │ 特徵工程  │→ │ 訓練驗證  │→ │ 部署服務  │→ │ 監控維運  │
│ Lake/DW  │   │ Feature  │   │ Pipeline │   │ Container│   │  Drift   │
│ Spark    │   │  Store   │   │ MLflow   │   │   K8s    │   │ 自動重訓  │
│ Airflow  │   │          │   │          │   │ A/B、藍綠 │   │          │
└──────────┘   └──────────┘   └──────────┘   └──────────┘   └──────────┘
       ↑                                                          │
       └──────────────── 效能低於門檻即觸發重訓 ────────────────────┘
```

### 特徵存放（Feature Store）要解決什麼

當 A 團隊做信用評分、B 團隊做詐欺偵測，兩邊都需要「使用者過去 30 天交易行為」時：

| 沒有 Feature Store | 有 Feature Store |
|---|---|
| 同一套特徵邏輯被實作兩次 | 定義寫一次，跨團隊共用 |
| 定義一改要兩邊同步，容易漏 | 單一來源，版本可追 |
| 離線訓練與線上服務口徑不一致（training-serving skew） | 同一份定義同時供離線與線上取用 |

**主要目的是消除跨團隊重複開發、降低維護成本並統一特徵定義**——不是為了省儲存空間、不是為了降低推論延遲，也不是為了管模型版本（那是模型註冊表與 MLflow 的職責）。

### 治理與可追溯性

| 機制 | 管什麼 | 代表工具 |
|---|---|---|
| 資料編目（Data Catalog） | 資料集清單、來源、擁有者、用途 | Apache Atlas、Amundsen |
| 資料來源追蹤（Data Lineage） | 從產生到應用的每一段轉換路徑 | 同上、流程編排工具內建血緣 |

| 實驗與模型追蹤 | 架構、超參數、訓練資料版本 | MLflow Tracking、Weights & Biases |
| 流程編排 | 排程、相依、重試 | Airflow、Kubeflow Pipelines、SageMaker Pipeline、Vertex AI |

## 37.8 易錯與陷阱

- [ ] 資料並行切的是**資料**、每個節點放**完整模型副本**；模型並行切的是**模型**、每個節點只放模型的一部分——不要反過來。
- [ ] PR 曲線的 X 軸是 **Recall**、Y 軸是 **Precision**；ROC 曲線的 X 軸是 **FPR**、Y 軸是 **TPR**——四個位置都別記混。
- [ ] SMOTE 是在少數類樣本與其近鄰之間**內插生成新點**，不是把既有樣本複製一份（那是隨機過採樣，也正是它最容易過擬合的原因）。
- [ ] 重抽樣、特徵篩選、標準化都要在**訓練／測試切分之後、只用訓練折 fit**；在全體資料上先做就是資料洩漏，不是「順序不重要的小細節」。
- [ ] 分層交叉驗證（Stratified K-Fold）解的是**類別比例失衡**；群組交叉驗證（Group K-Fold）解的是**同一受試者／同一門市的紀錄跨到測試集**——兩者解的問題不同，115Q1-17 同時需要後者。
- [ ] **在學習率等其他超參數不變的前提下**，大批次因梯度雜訊少而泛化可能變差；這不等於「大批次一定比較差」，實務上配合學習率調整可補回來。
- [ ] 梯度累積解的是**記憶體不足**（用多個小 batch 模擬大 batch），梯度壓縮解的是**網路傳輸壅塞**——不要拿梯度累積去回答通訊瓶頸的題目。
- [ ] Checkpointing 解的是**訓練中斷與容錯**，Early Stopping 解的是**過度訓練與資源浪費**——兩者都在訓練迴圈裡，但目的不同。
- [ ] 資料漂移變的是輸入分佈 P(X)，概念漂移變的是特徵與標籤的關聯 P(y|X)；用 KS 檢定或 KL 散度監控的是前者，後者要等標籤回流才看得出來。
- [ ] 類別不平衡使模型**偏向多數類**，與過擬合是不同機制，也與梯度爆炸無關——梯度爆炸主要來自網路深度、初始化與過大的學習率。
- [ ] Feature Store 的主要目的是**消除跨團隊重複開發、統一特徵定義**，不是省儲存空間，也不是管模型版本（那是模型註冊表／MLflow 的職責）。
- [ ] Parquet 是**欄式（Columnar，按 column 存放）**格式，好處是只讀需要的欄位；官方指引中譯作「列式」，看到時以英文 Columnar 為準。
- [ ] 「樣本數多」不等於「資料品質好」；標註大量錯誤時再加資料，對模型效能的幫助可能是負的。
- [ ] 為了吞吐量把影像**預先轉成固定特徵並快取反覆使用**，會讓資料增強失效、過擬合可能惡化——快取不是永遠都對的最佳化。
- [ ] 自注意力機制本身是**排列不變（Permutation Invariant）**的，順序資訊要靠**位置編碼加進詞嵌入**才有；模型對詞序不敏感時該先檢查位置編碼有沒有加上或被覆蓋，而不是加大模型或增加注意力頭數。
- [ ] 位置編碼提供的是「**序列中的位置**」，注意力遮罩（Attention Mask）提供的是「**哪些位置不准看**」——兩者職責不同；而且位置編碼不會讓模型自動理解章節或文件結構，那要靠切塊策略或階層式模型。
