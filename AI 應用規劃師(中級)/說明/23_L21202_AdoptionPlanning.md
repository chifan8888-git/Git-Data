# 23. L21202 AI導入規劃（40 分鐘）

> 一句話定位：初級只要求你知道「導入 AI 要先做 PoC」，中級則要求你在一段帶滿限制條件（樣本數、硬體、延遲、預算、法規、人力）的情境敘述裡，挑出唯一一個同時滿足全部條件的導入方案——這個知識點考的不是流程背誦，是**約束條件下的取捨判斷**。

## 學習目標
- 依「情境導向、資源盤點、彈性調整」三原則拆解一個 AI 導入專案的規劃內容
- 分辨 WBS、甘特圖、Sprint、任務追蹤工具各自解決的管理問題，不混用
- 在開發模式（商業服務／內部開發／委外）與部署模式（地端／公有雲／混合雲／邊緣）兩個軸上做出正確選型
- 用 PoC、影子模式、金絲雀發布與線上業務指標驗證導入成果，並指出「離線指標好就宣稱成功」的謬誤

## 23.1 導入規劃的三原則與資源盤點

### 三大原則（官方指引的骨架）

| 原則 | 內容 | 情境題怎麼出現 |
|---|---|---|
| **情境／目的導向** | 依產業特性與業務需求定義目標與範疇 | 零售聚焦銷售預測、醫療聚焦診斷輔助、製造聚焦瑕疵檢測 |
| **資源盤點** | 盤點現有資料、技術人力、硬體與預算，讓專案規模與資源匹配 | 「僅 2 名資料工程師＋1 名 ML 工程師」這種數字**是判準，不是背景** |
| **彈性調整** | 遇到需求變動或技術瓶頸時動態調整時程與策略 | 資料不完整就先花一個月修資料流程，而非硬推原時程 |

> **關鍵句：** 官方指引原文寫得很清楚——「導入規劃的重點不在於照表操課，而是靈活應對實際狀況」。凡是選項寫著「嚴格依照原訂時程執行」「等資料集蒐集到 10 萬筆再啟動」這類僵化敘述，幾乎都是誘答。

### 資源盤點的三類資源

```
人力資源 ── 專案負責人 / 資料工程師 / AI 模型開發者
         └─ UI/UX 設計師 / 業務顧問 / 系統架構師 / 測試工程師

硬體資源 ── GPU 伺服器（A100 類，加速訓練與推論）
         ├─ 雲端平台儲存與運算（AWS / GCP / Azure，彈性擴展）
         └─ 本地運算設備（小型試辦、資料敏感場景）

開發工具 ── Python / TensorFlow / PyTorch
         ├─ Spark、Hadoop（大資料處理）
         └─ Git 版本控制與原始碼管理機制
```

**盤點結果會直接決定技術方案。** 115Q1 第 23 題把這件事考到極致：瑕疵樣本只有 800 張、地端伺服器**無 GPU**、需 100 毫秒內完成推論、預算中等。四個條件同時成立時，唯一解是「預訓練模型做遷移學習 → 量化或蒸餾壓縮 → 部署於地端」。誘答分別違反其中一項：從零訓練大型 CNN（樣本不足＋預算不足）、暫緩導入等蒐集 10 萬筆（違反彈性原則）、上傳雲端用 AutoML（違反地端即時與資料不外流）。

## 23.2 專案設計與管理：四種工具不要混用

### 一張表分清楚

| 工具／方法 | 解決什麼問題 | 產出 | 關鍵字 |
|---|---|---|---|
| **工作分解結構（Work Breakdown Structure, WBS）** | 複雜任務**拆不開** | 由上而下的子任務樹，每項定義責任角色、預期成果、資源、時長 | 拆解、層級、責任歸屬 |
| **甘特圖（Gantt Chart）** | 時間安排與**重疊／關鍵路徑看不見** | 橫軸時間、縱軸任務的視覺化時程表 | 時程、里程碑、關鍵路徑（Critical Path） |
| **短衝（Sprint）／Scrum** | 需求變動快、技術**不確定性高** | 每輪 1～4 週的可交付增量（Increment） | 迭代、回饋、敏捷 |
| **任務追蹤工具** | 多部門多角色**資訊不同步** | 即時任務狀態與協作紀錄 | 看板、指派、通知 |

**常見誤判：** WBS 是「拆」，甘特圖是「排」。題目問「如何讓每個子任務的責任人與交付物明確」→ WBS；問「如何讓利害關係人一眼看出哪兩個階段時程重疊」→ 甘特圖。兩者是接力關係（先 WBS 拆、再上甘特圖排），不是替代關係。

### WBS 拆解示範（官方指引的例子）

```
資料準備
 ├─ 資料源盤點     → 責任：資料工程師 ／ 產出：可用資料來源清單
 ├─ 資料清理       → 責任：資料工程師 ／ 產出：清理後資料集
 ├─ 欄位標準化     → 責任：資料工程師 ／ 產出：統一格式與單位
 └─ 欄位對齊與標註 → 責任：標註團隊   ／ 產出：完成標註的訓練集
```

### Scrum 的 3 角色 / 5 活動 / 3 產出

| 類別 | 內容 |
|---|---|
| **角色** | Product Owner（定義需求與優先順序、維護 Product Backlog）／ Scrum Master（守流程、移除障礙）／ Development Team（跨職能，實際交付） |
| **活動** | Sprint Planning → Daily Scrum（約 15 分鐘）→ Sprint（1～4 週，常見 2 週）→ Sprint Review（展示成果收回饋）→ Sprint Retrospective（回顧檢討流程） |
| **產出** | Product Backlog（產品待辦）／ Sprint Backlog（本輪待辦）／ Increment（可運作的交付版本） |

> **最容易搞混的一組：** Sprint **Review** 是對外展示成果、收利害關係人回饋（談「產品」）；Sprint **Retrospective** 是對內檢討流程與協作問題（談「過程」）。選項若寫「Retrospective 用於向產品負責人展示模型訓練結果」即為錯誤。

### 任務追蹤工具的定位差異

| 工具 | 定位 | 適合 | 弱點 |
|---|---|---|---|
| **Trello** | 輕量看板（Kanban） | 小型團隊、原型初期 | 缺自動化工作流與依賴關係管理 |
| **Asana** | 結構化任務＋時間軸 | 跨部門協作的中大型專案 | 初期建立結構耗時 |
| **JIRA** | 問題追蹤＋敏捷支援 | 工程師／資料科學家主導的技術專案 | 非技術人員學習曲線陡 |
| **ClickUp** | 看板＋結構化＋里程碑 | 中型專案、需檢查清單與外部整合 | 選項過多、設定複雜 |

## 23.3 人員規劃＝跨部門協作角色與分工（必考）

**這一節是整份指引最穩定的送分區，而且考法固定。** 官方自我評量連續兩題都在問同一件事：

- 「AI 導入專案初期規劃階段，屬於**人員規劃**的重點內容是？」→ 正解「AI 專案所需的**跨部門協作角色**」
- 「最能避免部門間溝通斷裂與責任不清的規劃內容是？」→ 正解「建立**跨部門協作機制與角色分工**」

> **記死這句：人員規劃的重點是「角色與分工」，不是「招募幾個人」。** 誘答會給 API 規格設計、模型優化參數、作業系統版本（三個都是技術細節不是人員規劃），或是「由高階主管全權拍板模型選擇與部署方式」（集權不等於協作機制，反而加深斷裂）、「優先採購效能最佳的 GPU」（資源採購不解決溝通問題）。

### 七種角色與職責對照

| 角色 | 核心職責 | 能力需求 |
|---|---|---|
| **專案負責人（Project Manager）** | 整體協調與進度管理、制定時程、追蹤里程碑、**解決跨部門衝突**、對利害關係人溝通 | 專案管理知識（如 PMP）、跨團隊溝通 |
| **資料工程師** | 資料收集、清理、整合；多來源萃取與格式轉換 | 資料庫管理、ETL 流程 |
| **AI 模型開發者** | 模型設計、訓練與優化 | 機器學習／深度學習、Python、TensorFlow／PyTorch |
| **系統架構師** | 設計技術架構與**部署方案**，確保模型能整合進現有系統 | 雲端服務、系統整合、資料流與 API 設計 |
| **測試工程師** | 驗證模型效能與系統穩定性、壓力測試、輸出正確性檢查 | 測試設計、效能量測 |
| **UI/UX 設計師** | 設計業務人員易上手的操作體驗 | 介面設計、使用者研究 |
| **業務顧問** | 連結技術與業務需求、定義目標與關鍵指標 | 產業洞察、需求訪談 |

**易混：**「部署方式與伺服器架構規劃」是**系統架構師**，不是專案負責人也不是模型開發者；「跨部門目標不一致導致延誤，召開協調會議」是**專案負責人**。

### 跨部門協作機制的三個構件

```
A. 協作流程設計 ── 明確各部門在「資料提供、模型驗收、系統整合」上的責任邊界
                    → 避免重疊與漏洞

B. 例行同步節奏 ── 定期專案會議與進度報告（常見每週例會）
                    → 即時處理阻礙

C. 共用工具平台 ── 任務看板（Jira／Trello）＋ 文件平台（Notion／Confluence）
                    ＋ 即時通訊（Slack／Teams）
```

涉及的部門固定是這四類：**IT、業務、資料、法務／資安**。

## 23.4 AI 導入模式的選擇（最高頻考點）

這裡要拆成**兩個互相獨立的軸**來記，考題會分開考，也會混在同一題的限制條件裡。

### 軸一：開發模式（誰來做）

| 模式 | 優勢 | 挑戰／風險 | 適用情境 |
|---|---|---|---|
| **選用現有商業服務**（Low-code／No-code、AutoML、商用 API） | 快速部署、技術門檻低、彈性選用 | **彈性有限**（難調深層模型結構）、**長期訂閱成本高**、**資料需經雲端處理有隱私風險** | 技術能力有限、時間緊迫、資料敏感度低 |
| **內部技術團隊開發** | 掌控力強、可高度客製、保留技術自主性、符合內部法規與安全要求 | 初期成本高、需招聘與採購 GPU、缺乏人才時易失敗 | 有技術基礎且具**長期 AI 發展計畫** |
| **委外開發** | 借助外部成熟經驗、縮短開發時程 | **合約管理**（交付範圍與時程）、**資料安全**（敏感資料外流） | 缺內部技術能力但有預算 |

> 官方指引明確寫過反例：某零售企業因缺乏 AI 人才，內部開發耗時六個月且成效不佳。**「有預算沒人才」不該選內部開發**，這是委外或商業服務的場合。

### 軸二：部署模式（放在哪裡）——官方考過的決策表

| 部署模式 | 判準關鍵字 | 典型場域 | 代價 |
|---|---|---|---|
| **地端私有部署（On-Premise）** | **資料隱私、本地控制、法規要求資料不外流、資料主權** | 金融、醫療、政府、國防 | 需自購硬體、擴展彈性差、維運自理 |
| **公有雲（Public Cloud）** | 彈性擴展、免自建機房、快速起步、算力需求尖峰明顯 | 電商、新創、一般 SaaS | 資料須離開自有環境、長期用量大時成本高 |
| **混合雲（Hybrid Cloud）** | **敏感資料留地端 ＋ 大算力上雲**，兩個需求同時存在 | 醫院用公有雲 GPU 訓練但病患影像不得離院 | 架構與資料治理複雜度最高 |
| **邊緣部署（Edge）** | **低延遲、離線可用、頻寬受限、資料不上傳** | 產線工業相機、車載、IoT 終端 | 算力受限，模型須壓縮 |

**官方自我評量直球題：**「當 AI 導入規劃需評估系統部署模式時，若考量**資料隱私與本地控制**需求，應優先考慮？」→ 正解 **(B) 地端私有部署**。誘答是「第三方雲端部署」（資料外流）、「區塊鏈儲存方式」（答非所問）、「外包給 AI 公司」（那是開發模式不是部署模式，且資料同樣外流）。

> **關鍵切分法：只提「隱私＋本地控制」就選地端；同時出現「敏感資料不得外流」與「要用雲端算力」兩個需求，才是混合雲；強調「毫秒級延遲／斷網仍要運作」就是邊緣。** 別因為混合雲聽起來比較高級就選它。

### 三種延伸技術手段（跨到 L21203 的接合點）

| 情境 | 錯誤做法 | 正解 |
|---|---|---|
| 想用公有雲 GPU 訓練，但原始病患影像不得離院（HIPAA） | AES-256 加密後上傳（**資料仍離院、雲端解密後即明文**）、專線 VPN（只保護傳輸通道） | **聯邦學習（Federated Learning）**：院內本地訓練，只上傳梯度／權重更新至雲端聚合 |
| 已改成邊緣部署，仍達不到 200ms | 減少訓練資料量（只會讓模型變差）、批次推論（提高吞吐但**單張延遲更高**）、模型集成（延遲成倍） | **FP32 → INT8 量化**＋推論引擎加速（TensorRT／OpenVINO） |
| 即時推薦要 100ms、尖峰 3,000 QPS | 把即時資料先寫入資料倉儲再算特徵（引入分鐘級延遲）、3 人團隊上線上學習（維運風險過高） | 批次訓練建模型 ＋ REST API 推論 ＋ Kafka 串流特徵 ＋ **Redis／Feature Store 快取** |

## 23.5 導入成果驗證：PoC 與上線驗證策略

### PoC（概念驗證）的設計要點

| 要素 | 官方指引的說法 |
|---|---|
| **目標設定** | 明確且**可量化**，例如「測試推薦模型是否能提升銷售 5%」 |
| **範圍** | 聚焦**單一功能或情境**，小範圍測試 |
| **技術選型** | 不必過於複雜，可用現成工具（如 AutoML）快速建原型 |
| **流程覆蓋** | 涵蓋**從資料準備到模型測試的全流程** |
| **迭代節奏** | 快速迭代（Rapid Iteration），每輪限時 **1～2 週** |

**PoC 的三類驗證指標（缺一不可）：**

```
技術效能 ── 準確率、延遲時間
商業價值 ── 成本節省、效能提升、業務增長
使用者回饋 ── 問卷、訪談，了解可用性與操作體驗
```

### 上線驗證策略的分工

| 策略 | 使用者看得到新模型嗎 | 能量到真實業務指標嗎 | 適用時機 |
|---|---|---|---|
| **回測（Backtesting）** | 否 | 否（仍是歷史日誌推估，有反饋迴圈偏誤） | 最早期粗篩 |
| **影子模式（Shadow Mode）** | **否**（僅後端比對輸出差異） | 否 | 驗證系統負載與輸出一致性 |
| **金絲雀發布（Canary Release）** | **是**（1～5% 流量） | **是**（CTR、CVR、停留時間） | 可控風險下量化真實業務指標 |
| **漸進式部署（Phased Rollout）** | 是（分階段擴大範圍） | 是 | 降低對既有流程的衝擊 |
| **負載測試（Load Testing）** | 否 | 否（只驗承載能力） | 上線前的容量驗證 |

**漸進式部署的兩題官方考法要一起記：**

- **起點怎麼選**：醫院導入輔助診斷 → 從**單一專科（如放射科）或特定病房**開始再擴全院。誘答「先部署在病例量最高的急診」錯在急診風險與壓力最高；「僅夜班啟用」錯在樣本代表性不足。**低風險、可控、可收斂回饋 > 樣本量大。**
- **擴量中出問題怎麼辦**：流量升到 30% 時延遲明顯上升但轉換率略升 → **暫停擴量、做效能剖析與優化後再繼續**。不是全面上線（擴大災情），也不是直接全部回滾（白白丟掉已驗證的業務價值），更不是放著不管。

### 成效評估最經典的謬誤

> 「AUC 高達 0.91，模型表現優異，AI 導入成效良好。」

這句話錯在**只用離線指標宣稱導入成功**。同一份數據裡，點擊率從 3.2% 掉到 3.1%、推論成本每月多 12,000 元；平均訂單金額雖從 850 元升到 1,020 元，也可能來自促銷檔期或客群結構改變，**必須用 A/B 測試排除干擾才能歸因於模型**。

```
離線指標（AUC、NDCG、RMSE）── 衡量模型在歷史資料上的能力
                              └─ 好 ≠ 導入成功
線上業務指標（CTR、CVR、營收、成本）── 衡量導入成效
                              └─ 必須搭配 A/B 測試做因果歸因
```

## 23.6 規劃成果的整合輸出（五份文件）

導入規劃階段結束時要交出的東西是固定的五項，常以「哪一份文件包含 X」的形式考：

| 產出 | 內容重點 |
|---|---|
| **導入規劃文件（Implementation Plan Document）** | 專案背景、導入目標、執行策略、專案範疇、主要任務、時程、團隊結構、預算與資源需求——**貫穿全程的核心文件** |
| **專案成果彙整報告（Planning Summary）** | 關鍵決策點、初步原型成果、評估指標結果、團隊分工、潛在風險預警——**給高階主管快速掌握** |
| **甘特圖與時程規劃** | 階段、排程、里程碑、責任歸屬、資源分配 |
| **資源估算與成本預算表** | 人力／硬體／軟體／外部合作，含資金來源（自有／補助／外包）與成本變動情境 |
| **利害關係人審查紀錄（Stakeholder Review）** | 技術、業務、法務／資安、高階管理層的意見回饋與決議——**是進入實作階段的前提條件** |

> **觀念題常考：** 驗收標準與審查機制屬於**規劃階段**的工作，不是做完才補。規劃成果必須先通過利害關係人審查，專案才具備進入實作的條件。

## 23.7 官方考過什麼

在 114-2 與 115-1 兩份官方公告試題（共 100 題）中，可歸為 AI 導入規劃相關的共 **8 題**；官方《學習指引》第四章自我評量另有 3 題直接對應本知識點。

### 官方公告試題

| # | 考點 | 怎麼問 | 正解思路 |
|---|---|---|---|
| 114Q2-23 | 漸進式部署的起點 | 醫院導入輔助診斷如何降低臨床衝擊 | **單一專科或特定病房**先行；急診量大但風險高，夜班代表性不足 |
| 115Q1-19 | 導入成效評估 | 「AUC 0.91 所以成效良好」錯在哪 | 只看**離線指標**、忽略 CTR 與成本等線上業務指標，且未做 A/B 歸因 |
| 115Q1-20 | 導入技術規劃組合 | 100ms／3,000 QPS／3 人團隊，五項規劃保留哪些 | 保留批次訓練＋REST API＋Kafka，**移除資料倉儲路徑**，加入 Redis／Feature Store |
| 115Q1-23 | 資源受限下的第一階段規劃 | 800 張樣本、無 GPU、100ms、預算中等 | **遷移學習 ＋ 量化／蒸餾 ＋ 地端部署**；暫緩導入與上雲 AutoML 皆違反限制 |
| 115Q1-40 | 邊緣部署仍超時 | 不換硬體如何再降延遲 | **FP32→INT8 量化**＋推論加速；批次推論反而拉高單張延遲 |
| 115Q1-43 | 上線前的驗證策略 | 離線指標優異，如何在可控風險下量真實業務指標 | **金絲雀發布**（1–5% 流量）；影子模式量不到互動、回測仍是離線 |
| 115Q1-46 | 混合雲的合規解法 | 要用公有雲 GPU 但原始影像不得離院 | **聯邦學習**只上傳模型更新；加密上傳與 VPN 都讓資料離院 |
| 115Q1-47 | 漸進式部署的中途處置 | 30% 流量時延遲惡化、轉換率略升 | **暫停擴量、效能優化後再放量**；全推與全回滾都過當 |

### 官方學習指引自我評量（第四章）

| # | 考點 | 正解 | 誘答設計 |
|---|---|---|---|
| 第 4 題 | 人員規劃的重點 | **AI 專案所需的跨部門協作角色** | API 規格設計、模型優化參數、作業系統版本（皆為技術細節） |
| 第 5 題 | 避免部門溝通斷裂與責任不清 | **建立跨部門協作機制與角色分工** | 追最新演算法研究、高階主管全權拍板、優先採購最強 GPU |

## 23.8 易錯與陷阱

- [ ] **人員規劃＝跨部門角色與分工，不是招募人數或技術規格** —— 看到 API 規格、模型參數、OS 版本出現在「人員規劃」選項中一律刪。
- [ ] **「資料隱私與本地控制」→ 地端私有部署，不是混合雲** —— 混合雲要等到題幹**同時**出現「敏感資料不得外流」與「需要雲端算力」才成立。
- [ ] **「外包給 AI 公司」是開發模式，不是部署模式** —— 問部署模式的題目若選委外，等於答錯類別。
- [ ] **WBS 是「拆解」，甘特圖是「排程」** —— 責任歸屬與交付物看 WBS；時程重疊與關鍵路徑看甘特圖。
- [ ] **Sprint Review 對外展示成果，Sprint Retrospective 對內檢討流程** —— 兩者對象與主題都不同。
- [ ] **有預算但沒 AI 人才 → 委外或商業服務，不是內部開發** —— 官方指引明寫內部開發需「充足技術基礎作為前提」。
- [ ] **商業服務的三大代價是彈性有限、長期訂閱成本、資料隱私風險** —— 不是「準確率一定較低」。
- [ ] **離線指標好 ≠ 導入成功** —— AUC／NDCG 衡量模型能力，CTR／CVR／營收／成本才衡量導入成效，且需 A/B 測試做因果歸因。
- [ ] **影子模式量不到真實業務指標** —— 使用者看不到新模型結果，就沒有點擊與購買行為可量；要量業務指標得用金絲雀發布。
- [ ] **漸進式部署的起點選「低風險可控」，不是「樣本量最大」** —— 急診量大但壓力高，不是好起點。
- [ ] **擴量途中出問題 → 暫停並優化，不是立刻全回滾** —— 回滾會丟掉已驗證的業務價值，屬處置過當。
- [ ] **批次推論提升的是吞吐量，不是單筆延遲** —— 逐件即時檢測的情境下反而更慢。
- [ ] **資料不足時的正解是遷移學習，不是「暫緩專案等蒐集十萬筆」** —— 後者違反導入規劃的彈性調整原則。
- [ ] **加密上傳、VPN 都無法滿足「原始資料不得離開院內」** —— 資料仍然離開了原環境；要用聯邦學習。
- [ ] **驗收標準與審查機制在規劃階段就要訂** —— 利害關係人審查紀錄是進入實作階段的前提，不是事後補件。
