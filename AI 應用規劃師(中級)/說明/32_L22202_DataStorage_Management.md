# 32. L22202 數據儲存與管理（45 分鐘）

> 一句話定位：這一節是第四章「大數據處理技術」的骨幹，把資料從「存得下」推進到「存得對、找得快、管得住」。
> 初級只要求你知道「資料要放在資料庫裡」；中級要求你面對一個情境，**選出正確的儲存架構、說明取捨代價、並指出治理機制擺在哪一層**。

## 學習目標

- 精準區辨資料倉儲、資料湖、資料湖倉，以及 ETL／ELT、Schema-on-Write／Schema-on-Read
- 說明分散式儲存的分片與副本差異，並用 CAP 與一致性模型解釋系統取捨

## 32.1 資料型態決定儲存選型

官方指引把這一節的第一個判斷點放在「資料長什麼樣子」。題目幾乎都從情境敘述倒推儲存技術，所以這張表是所有選型題的起點。

| 維度 | 結構化（Structured） | 半結構化（Semi-structured） | 非結構化（Unstructured） |
|---|---|---|---|
| **特徵** | 固定欄位、固定型別 | 有層次與標記，但欄位可變 | 無預定格式 |
| **典型格式** | 資料表、CSV | JSON、XML、YAML | 文字、圖片、音訊、影片、PDF |
| **典型來源** | ERP、CRM、POS | API 回傳、IoT 封包、網頁擷取 | 社群貼文、客服錄音、監視影像 |
| **儲存方式** | 關聯式資料庫（RDBMS） | 文件型 NoSQL、全文搜尋引擎、資料湖 | 物件儲存（S3、MinIO）、分散式檔案系統（HDFS） |
| **查詢方式** | SQL | 路徑／巢狀欄位查詢、倒排索引 | 靠 metadata、標籤與內容索引間接查 |
| **優勢** | SQL 查詢、完整性約束、ACID | 格式彈性、易整合異質來源 | 可容納任何內容、單位成本低 |
| **限制** | 結構變更不靈活 | 缺少結構約束，驗證邏輯要自己寫 | 難以直接搜尋比對，需外部標註 |

### 實務上是混合的

一個電商平台同時擁有三種型態：訂單紀錄（結構化）、商品描述與規格（半結構化）、商品圖片與顧客留言（非結構化）。**考題喜歡在這裡設陷阱：給一個混合情境，然後把「全部用同一種資料庫」放進選項。** 正解通常是依需求分開選用，也就是多元持久化（Polyglot Persistence）。

## 32.2 關聯式資料庫與 SQL 基本功

### 正規化 vs 反正規化

| 維度 | 正規化（Normalization） | 反正規化（Denormalization） |
|---|---|---|
| **做法** | 拆表、用外鍵關聯，消除重複欄位 | 刻意保留冗餘欄位或預先併表 |
| **主要目的** | 減少資料冗餘、避免新增／更新／刪除異常 | 減少 JOIN 次數、加快讀取 |
| **寫入成本** | 低（一處修改即可） | 高（同一事實要同步多處） |
| **讀取成本** | 高（需要多表 JOIN） | 低 |
| **典型場景** | OLTP 交易系統、庫存扣減 | OLAP 分析、報表、資料倉儲的星狀結構 |

正規化層級只需要記到判斷層次：**1NF** 欄位不可再分割；**2NF** 在 1NF 之上消除「非鍵欄位只相依於複合主鍵一部分」的部分相依；**3NF** 在 2NF 之上消除「非鍵欄位透過另一個非鍵欄位間接相依於主鍵」的遞移相依。

### 會考的 SQL 語意

```sql
SELECT c.customer_name,
       p.category,
       SUM(o.amount) AS total_amount
FROM   orders    AS o
JOIN   customers AS c ON o.customer_id = c.customer_id
JOIN   products  AS p ON o.product_id  = p.product_id
WHERE  o.order_date >= '2025-01-01'     -- 聚合「前」過濾單筆資料列
GROUP  BY c.customer_name, p.category
HAVING SUM(o.amount) > 10000            -- 聚合「後」過濾群組
ORDER  BY total_amount DESC
LIMIT  10;
```

兩個最常被考的語意差別：

| 關鍵字 | 作用時機 | 過濾對象 |
|---|---|---|
| `WHERE` | `GROUP BY` **之前** | 單筆資料列 |
| `HAVING` | `GROUP BY` **之後** | 聚合後的群組 |

JOIN 型態要能和集合運算對上：

| JOIN | 結果 | 集合語意 |
|---|---|---|
| `INNER JOIN` | 只保留兩表都有對應鍵值的列 | 交集 |
| `LEFT OUTER JOIN` | 左表全留，右表無對應者填 `NULL` | 左表為主 |
| `RIGHT OUTER JOIN` | 右表全留 | 右表為主 |
| `FULL OUTER JOIN` | 兩表全留 | 聯集 |
| `CROSS JOIN` | 每一列兩兩配對 | 笛卡兒積 |

> 這組語意在 pandas 題裡也會考：`pd.merge(..., how='inner')` 就是交集、`how='outer'` 就是聯集。115-1 第 47 題考的正是這個。

### ACID 四特性（高頻單點題）

| 字母 | 名稱 | 定義（一句話） | 常見誘答 |
|---|---|---|---|
| **A** | 原子性（Atomicity） | 一筆交易的所有操作全做完或全不做，中途失敗要回復（Rollback） | 誤寫成「多節點自動同步」 |
| **C** | 一致性（Consistency） | 交易前後資料都必須符合主鍵、外鍵、約束等完整性規則 | 誤寫成「所有副本資料相同」 |
| **I** | 隔離性（Isolation） | 並行交易彼此不干擾，結果如同各自單獨執行 | 誤寫成「交易不能同時執行」 |
| **D** | 持久性（Durability） | 一旦成功提交，變更永久保存，當機也不遺失 | 誤寫成「資料永遠不可刪除」 |

**注意 C 的雙重身分**：ACID 的 C 是「符合資料庫完整性規則」，CAP 的 C 是「所有節點讀到同一份最新資料」。兩個 C 不是同一件事，考題會拿這點設誘答。

## 32.3 NoSQL 四大型態

NoSQL 的原意是 **Not Only SQL**，不是「不能用 SQL」——Cassandra 有 CQL、許多文件型資料庫也提供類 SQL 介面。它真正放棄的是「固定 schema 與跨表強交易」，換回擴展性與彈性。

| 型態 | 資料模型 | 查詢特性 | 代表產品 | 最適情境 |
|---|---|---|---|---|
| **鍵值（Key-Value）** | key → value（value 對資料庫不透明） | 依 key 直接取值；無法直接用 value 內容查 | Redis、Memcached、DynamoDB | 快取、Session、計數器、排行榜 |
| **文件（Document）** | key → JSON／BSON 文件，可巢狀 | 可查巢狀欄位、可建二級索引 | MongoDB、CouchDB | 欄位因品項而異的商品目錄、內容管理 |
| **欄族（Column-family／Wide-column）** | Row Key ＋（欄族 → 大量稀疏欄） | 依 Row Key 範圍掃描，寫入吞吐極高 | HBase、Cassandra | 時間序列、感測器紀錄、超寬稀疏表 |
| **圖（Graph）** | 節點（Node）／邊（Edge）／屬性（Property） | 多跳關聯遍歷、最短路徑 | Neo4j、JanusGraph | 社群關係、詐欺網路、知識圖譜 |

另外兩類常在情境題中與上表並列：

- **向量資料庫（Vector Database）**：Milvus、Qdrant、pgvector。存放嵌入向量，用近似最近鄰（Approximate Nearest Neighbor, ANN）索引做相似度搜尋，是 RAG 與推薦系統的標配。
- **搜尋引擎型**：Elasticsearch、OpenSearch。以倒排索引（Inverted Index）支撐全文檢索，屬近即時（near real-time）索引，**不保證強一致性**。

### 圖資料庫的建模原則

官方考過屬性圖的建模：**「行為」若帶有屬性（時間戳記、裝置類型），應該建成連接兩個節點的「邊」，並把屬性掛在邊上。**

```
  (User:小明) ──[LIKED {ts:2025-03-01, device:"iOS"}]──► (Post:#1234)
       │
       └────────[FOLLOWS {since:2024-08}]──────────────► (User:小華)
```

把「按讚」獨立成節點會讓結構與查詢成本膨脹；把它寫進使用者節點的屬性則會弄丟「是對哪一篇貼文」的對應關係。

若目標是**知識圖譜＋語意推理**，標準答案會轉向 **RDF 三元組（Subject–Predicate–Object）**，因為它是 W3C 標準語意模型，可搭配本體（Ontology）與推理引擎；屬性圖偏向高效遍歷，語意推理與跨系統互通能力不如 RDF。

## 32.4 資料倉儲、資料湖、資料湖倉

這是本知識點表格題密度最高的地方。

| 維度 | 資料倉儲（Data Warehouse） | 資料湖（Data Lake） | 資料湖倉（Data Lakehouse） |
|---|---|---|---|
| **存什麼** | 已清洗、已建模的結構化資料 | 原始格式的結構化／半結構化／非結構化資料 | 開放檔案格式的原始與精煉資料並存 |
| **Schema 時機** | Schema-on-Write（寫入時就要符合結構） | Schema-on-Read（讀取時才套用結構） | 底層 Schema-on-Read，表層提供 schema 強制與演進 |
| **資料處理** | ETL | ELT | ELT ＋ 分層（Bronze／Silver／Gold） |
| **主要使用者** | BI 分析師、報表 | 資料科學家、ML 工程師 | 兩者共用同一份資料 |
| **儲存成本** | 高（專有格式、需先加工） | 低（物件儲存、按量計費） | 低（沿用物件儲存） |
| **查詢效能** | 高且穩定 | 視格式與分區而定，落差大 | 靠 metadata 層逼近倉儲 |
| **交易支援** | 完整 ACID | 原生沒有 | 由 metadata 層補上 ACID |
| **代表技術** | Snowflake、BigQuery、Redshift | HDFS、Amazon S3、Azure Data Lake | Delta Lake、Apache Iceberg、Apache Hudi |
| **失敗模式** | 加新來源要重做建模，彈性差 | 無治理就退化成資料沼澤（Data Swamp） | 架構複雜、metadata 層需維運 |

### ETL vs ELT

```
ETL（傳統倉儲）
  來源系統 ─►[E 擷取]─►[T 轉換：獨立的轉換引擎]─►[L 載入]─► 資料倉儲
                              ▲ 只有符合結構的資料進得去，原始資料通常不留

ELT（雲端／資料湖）
  來源系統 ─►[E 擷取]─►[L 載入：原始資料直接進湖]─►[T 轉換：用目標平台算力]─► 分析
                              ▲ 原始資料完整保留，轉換邏輯可重跑
```

| 維度 | ETL | ELT |
|---|---|---|
| **轉換發生位置** | 載入**之前**，在獨立的轉換引擎 | 載入**之後**，在目標儲存平台內部 |
| **原始資料** | 通常不保留 | 完整保留，可重新加工 |
| **對目標算力需求** | 低 | 高（因此仰賴雲端彈性算力） |
| **適合資料型態** | 結構化為主 | 三種型態皆可 |
| **搭配架構** | Schema-on-Write 的資料倉儲 | Schema-on-Read 的資料湖／湖倉 |

### Schema-on-Write vs Schema-on-Read

| | Schema-on-Write | Schema-on-Read |
|---|---|---|
| **檢查時機** | 寫入時驗證，不合格就拒收 | 寫入照單全收，讀取時才解讀 |
| **好處** | 資料品質有保證、查詢可預先最佳化 | 彈性高、新增來源成本低、不丟資訊 |
| **代價** | 結構變更要做 schema migration | 品質問題延後爆發，讀取端要自行處理髒資料 |
| **對應架構** | 資料倉儲、RDBMS | 資料湖、物件儲存 |

## 32.5 分散式儲存：分片、副本、CAP

### HDFS 架構

```
                    ┌──────────────────────────────────┐
   Client ─①請求──► │  NameNode（主節點）              │
          ◄─②位置── │   ‧ 命名空間／目錄樹             │  只管元資料，
                    │   ‧ 檔案 → 區塊清單              │  實際資料不經過它
                    │   ‧ 區塊 → 所在 DataNode 對照表  │
                    └──────────────┬───────────────────┘
                        心跳 ＋ 區塊報告（DataNode 定期回報）
              ┌────────────────────┼────────────────────┐
              ▼                    ▼                    ▼
        ┌───────────┐        ┌───────────┐        ┌───────────┐
        │ DataNode1 │        │ DataNode2 │        │ DataNode3 │
        │ blk_1 ▓   │        │ blk_1 ▓   │        │ blk_1 ▓   │
        │ blk_2 ▓   │        │ blk_3 ▓   │        │ blk_2 ▓   │
        └───────────┘        └───────────┘        └───────────┘
              ▲ ③Client 直接與 DataNode 讀寫資料區塊
```

| 項目 | 內容 |
|---|---|
| **NameNode** | 只存元資料（命名空間、檔案→區塊、區塊→節點位置），不存實際檔案內容 |
| **DataNode** | 存放實際資料區塊，定期送心跳與區塊報告給 NameNode |
| **預設區塊大小** | 128 MB（Hadoop 2.x 起；1.x 為 64 MB） |
| **預設副本因子** | 3 份，機架感知配置：1 份放寫入端所在機架、另 2 份放到別的機架 |
| **寫入模型** | 一次寫入多次讀取（write-once-read-many），可 append，不支援任意位置覆寫 |
| **不擅長** | 大量小檔案（元資料塞爆 NameNode 記憶體）、低延遲隨機讀取 |
| **Secondary NameNode** | 負責 fsimage 與 editlog 合併的檢查點工作，**不是**熱備援；高可用要用 Active／Standby NameNode 搭配 JournalNode |

### 分片（Sharding）vs 副本（Replication）

兩者常被放在同一題的選項中互當誘答，必須分得乾淨。

| 維度 | 分片（Sharding／Partitioning） | 副本（Replication） |
|---|---|---|
| **切的是什麼** | **不同**的資料放到不同節點（水平切分） | **同一份**資料複製到多個節點 |
| **主要目的** | 突破單節點容量與吞吐上限、負載均衡 | 容錯、高可用、分攤讀取流量 |
| **增加節點的效果** | 總容量與寫入吞吐近線性成長 | 容量不變，讀取能力與耐故障度上升 |
| **主要風險** | 分片鍵選不好造成熱點（Hotspot）、跨分片 JOIN 昂貴 | 副本間同步延遲造成讀到舊值 |

分片策略：**範圍分片**（依時間或數值區間切，範圍查詢快但容易熱點）、**雜湊分片**（分布均勻但範圍查詢要掃全部分片）、**查表／目錄分片**（彈性最高，但查表本身可能成為單點）。

### CAP 定理

```
                C 一致性（Consistency）
               每次讀取都拿到最新寫入值
                        ╱ ╲
       CP：分區時寧可      ╲   CA：只在單機或
       拒絕服務也要正確      ╲  「保證不分區」時成立
       （HBase、ZooKeeper）   ╲ （分散式環境不現實）
                ╱              ╲
  A 可用性 ─────────────────────── P 分區容忍性
  每個請求都有非錯誤回應           網路斷裂時仍能運作
         AP：分區時照樣回應，可能是舊值（Cassandra、DynamoDB）
```

**精確說法：只有在網路分區（P）實際發生時，系統才被迫在 C 與 A 之間二選一。** 網路正常時，系統可以同時提供強一致與高可用。由於分散式系統無法假設網路永不斷線，P 事實上是必選項，所以真正的選擇是 CP 或 AP。

### 一致性模型與 ACID／BASE

| 模型 | 保證 | 代價 | 適用 |
|---|---|---|---|
| **強一致性（Strong Consistency）** | 寫入成功後，任何讀取都看得到最新值 | 需跨節點協調（Paxos／Raft），延遲高、分區時可能不可用 | 金融交易、帳務、庫存扣減 |
| **最終一致性（Eventual Consistency）** | 允許短暫不同步，但**最終會收斂到一致** | 中間可能讀到舊值 | 物件儲存、資料湖、社群動態、瀏覽計數 |

| | ACID | BASE |
|---|---|---|
| **全稱** | Atomicity／Consistency／Isolation／Durability | Basically Available、Soft state、Eventually consistent |
| **立場** | 寧可拒絕服務也要正確 | 寧可回舊值也要有回應 |
| **典型系統** | RDBMS、Delta Lake／Iceberg 的交易層 | Cassandra、DynamoDB、Amazon S3 |

寫入衝突的補強機制（官方指引明列）：**單一寫入者原則、分區層級鎖定、版本號或時間戳記排序**。

## 32.6 儲存效能優化與查詢加速

> **用語提醒**：Columnar Storage 在台灣慣稱「欄式儲存」（欄＝column），但官方《學習指引》原文寫作「列式儲存」（大陸用語）。本節一律附英文 Columnar／Row-oriented，兩種中文寫法都要對得上。

| 技術 | 做什麼 | 為什麼快 | 反效果 |
|---|---|---|---|
| **分區（Partitioning）** | 依時間、地區等欄位把資料切成目錄或區塊 | 查詢只掃描命中的分區（Partition Pruning） | 分區過細產生大量小檔案，反而變慢 |
| **欄式儲存（Columnar，Parquet／ORC）** | 同一欄的值連續存放 | 只讀需要的欄；同型別資料壓縮率高 | 逐列增刪改成本高，不適合 OLTP |
| **壓縮（Snappy／ZSTD）** | 壓小檔案體積 | 降低磁碟用量與 I/O 傳輸成本 | 解壓縮吃 CPU；壓縮率與速度需權衡 |
| **欄位裁剪與投影（Column Pruning）** | 只載入 `SELECT` 用到的欄位 | 大幅減少讀取量 | 要搭配欄式格式才有明顯效果 |
| **儲存分層（Storage Tiering）** | 熱資料放 SSD、冷資料放 HDD 或雲端封存 | 用成本換取整體效能平衡 | 冷資料取回有延遲與取回費用 |
| **物化檢視（Materialized View）** | 預先算好結果並實際存下來 | 重複性查詢（日報、排行榜）直接讀結果 | 底層變動後需刷新，有資料新鮮度落差 |
| **索引（Index）** | B-tree、倒排索引、文字索引 | 快速定位符合條件的資料列 | 佔空間、拖慢寫入 |
| **查詢引擎最佳化** | Spark Catalyst、Presto CBO（成本導向最佳化器） | 自動重排執行計畫、下推述詞 | 統計資訊過期會選錯計畫 |
| **查詢資源管控（Throttling）** | 設定查詢優先序與資源上限 | 避免單一查詢拖垮整個叢集 | 需調參，設定過嚴會誤殺正常查詢 |

**檢視（View）vs 物化檢視（Materialized View）**：一般 View 只是查詢的命名別名，每次查詢都重新計算、不佔額外儲存；Materialized View 實際把結果存下來，讀得快但需要刷新機制。

## 32.7 資料治理、版本控制與存取控管

### 元資料與資料血緣

元資料（Metadata）是「描述資料的資料」——來源、格式、欄位名稱與定義、建立與更新時間、關聯表格與模型依存關係。把元資料集中管理就形成**資料目錄（Data Catalog）**，進而支撐：

- **資料血緣（Data Lineage）**：追蹤資料從來源到使用的完整流向，出錯時能往回溯源
- 自動化的資料探索與分析前處理
- 跨部門共享時的欄位定義對齊

### 資料版本控制

| 機制 | 內容 | 代表技術 |
|---|---|---|
| **版本標記與變更紀錄** | 每次匯入或修改賦予版本標籤，建立可追溯的歷史 | Delta Lake **Time Travel**、Apache Hudi **Incremental Query** |
| **資料快照與版本回溯** | 定期建立快照，支援誤寫復原、資料還原與模型再訓練 | Apache Iceberg Snapshot |

對 AI 專案來說，這一項的意義是**可重現性（Reproducibility）**：沒有資料版本，就無法說明「這個模型是用哪一份資料訓練出來的」，實驗結果也無從複製。

### 存取控管模型（官方指引明列四種）

| 模型 | 全稱 | 控管依據 | 優點 | 適用情境 |
|---|---|---|---|---|
| **RBAC** | Role-Based Access Control | 使用者所屬**角色**（工程師／分析師／主管） | 邏輯清楚、實作簡單 | 中小企業、部門制組織 |
| **ABAC** | Attribute-Based Access Control | 使用者屬性＋資料屬性＋**環境條件**（地點、時間、裝置） | 彈性高、支援細緻動態授權 | 大型企業、高安全性情境 |
| **PBAC** | Policy-Based Access Control | 預先定義的**複合策略規則** | 可統一控管多系統，支援複雜條件語法（OPA／Rego） | 雲端平台、跨部門跨系統整合 |
| **DAC** | Discretionary Access Control | **資料擁有者**自行決定誰能存取 | 彈性高、上手快 | 研發團隊、開發環境、小型專案 |

記憶線索：RBAC 看「你的角色是什麼」、ABAC 看「你與資料與當下環境的屬性」、PBAC 看「策略規則怎麼寫」、DAC 看「擁有者說了算」。

### 稽核與 Zero Trust

存取稽核要留下：查詢／修改／刪除的操作日誌、存取者身分與角色、時間戳記、來源設備資訊，並能匯出稽核報告供 GDPR、CCPA 等合規查核。

Zero Trust（零信任）的前提是「**不預設信任任何人與裝置**」，連內網使用者也要持續驗證。四個落到資料層的原則：

| 原則 | 內容 |
|---|---|
| **最小權限（Least Privilege）** | 只給完成任務所需的最小資料範圍 |
| **動態授權（Just-In-Time Access）** | 依行為、時間、裝置、網路位置動態調整，避免長期權限累積 |
| **持續驗證（Continuous Authentication）** | 搭配多因子驗證與行為分析 |
| **微分段（Microsegmentation）** | 資料資源分區隔離，避免單點被攻破後橫向擴散 |

## 32.9 易錯與陷阱

- [ ] **分片（Sharding）是把不同資料水平切到不同節點**，不是把同一份資料複製多份——後者是副本（Replication）
- [ ] **副本提升的是可用性與讀取吞吐**，不是總儲存容量；要擴容量得靠分片
- [ ] **Schema-on-Read 對應資料湖**（讀取時才套結構），不是資料倉儲；**Schema-on-Write 才對應資料倉儲**
- [ ] **ETL 的轉換發生在載入之前**，不是之後；**ELT 才是先載入原始資料、再在目標平台內轉換**
- [ ] **資料湖倉（Lakehouse）是在資料湖上補 ACID 與治理能力**，不是資料倉儲的新名字，也不是資料湖的別稱
- [ ] **資料湖存的是原始未轉換、未清洗的資料**，不是「已清洗但還沒建模的資料」；缺乏治理會退化成資料沼澤
- [ ] **ACID 的 C 指符合完整性規則**（主鍵、外鍵、約束），不是 CAP 的 C（各節點讀到同一份最新資料）
- [ ] **CAP 是在網路分區發生時才被迫二選一**，不是「任何情況下都只能三選二」；網路正常時可同時強一致又高可用
- [ ] **最終一致性是「暫時不同步、最後會收斂」**，不是「永遠不保證一致」
- [ ] **NoSQL 是 Not Only SQL**，不是「不能用 SQL 查詢」；Cassandra 有 CQL，多數產品也提供類 SQL 介面
- [ ] **鍵值資料庫是依 key 取值**，value 的內容對資料庫不透明，不能像文件型那樣直接查巢狀欄位
- [ ] **欄族（Wide-column）資料庫是稀疏寬表的資料模型**，不是「欄式儲存格式」；Parquet／ORC 才是檔案格式
- [ ] **圖資料庫中帶屬性的互動行為要建成邊、屬性掛在邊上**，不是建成獨立節點，也不是寫進某一端的節點屬性
- [ ] **需要語意推理的知識圖譜選 RDF 三元組**，不是把資訊全塞進屬性圖的節點屬性
- [ ] **HDFS 的 NameNode 只管元資料**，實際資料區塊在 DataNode，Client 取得位置後是直接與 DataNode 讀寫的
- [ ] **Secondary NameNode 是做檢查點合併的角色**，不是熱備援；高可用要靠 Active／Standby NameNode 搭配 JournalNode
- [ ] **HDFS 不擅長大量小檔案與低延遲隨機讀取**，不是「任何情境都比關聯式資料庫快」
- [ ] **欄式儲存（Columnar）利於只讀少數欄位的分析查詢**，不利於逐列增刪改，因此不適合當 OLTP 主儲存
- [ ] **分區（Partitioning）縮小的是掃描範圍**，不是「預先算好結果」——預先算好結果是物化檢視
- [ ] **物化檢視實際存下結果、需要刷新**；一般檢視（View）只是查詢別名、不佔額外儲存
- [ ] **壓縮省的是空間與 I/O 成本**，突破不了單節點的容量與運算上限
- [ ] **正規化減少冗餘但增加 JOIN 成本**，反正規化則相反；OLTP 偏正規化、OLAP 偏反正規化
- [ ] **`WHERE` 在聚合前過濾資料列、`HAVING` 在聚合後過濾群組**，兩者位置不能互換
- [ ] **`INNER JOIN` 取交集、`FULL OUTER JOIN` 取聯集**；pandas 的 `how='inner'`／`how='outer'` 是同一套語意
- [ ] **RBAC 依角色授權，ABAC 才把時間、地點、裝置等環境條件納入判斷**，兩者不是同義詞
- [ ] **DAC 由資料擁有者自行決定授權**，不是由系統管理員統一指派——統一指派較接近 RBAC 的運作方式
- [ ] **Zero Trust 的前提是連內網使用者也不預設信任**，不是「把防火牆加厚、把外部擋在門外」
- [ ] **Delta Lake 的 Time Travel 是資料版本回溯**，不是備份還原機制；它讀的是同一份儲存上的歷史版本
- [ ] **物件儲存（S3）是扁平的 key 命名空間**，介面上的「資料夾」其實是 key 前綴，不是真正的階層式檔案系統
- [ ] 遇到「同一情境同時要交易、彈性 schema 與向量搜尋」的題目，**正解通常是分別選用最適資料庫**，而不是為了統一技術棧全用同一種
