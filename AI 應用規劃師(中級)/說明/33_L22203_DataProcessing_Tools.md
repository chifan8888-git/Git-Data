## 33.1 資料轉換：把「乾淨」變成「可運算」

清理完的資料只是沒有髒值，還不等於模型吃得下。官方指引把這段拆成四類作業：

| 類別 | 做什麼 | 典型操作 | 最常被考的副作用 |
|---|---|---|---|
| **型別轉換與欄位整理** | 統一型別、命名與結構 | `str → int`、時間統一為 datetime／ISO 8601、`cust_id → customer_id`、欄位合併或拆分 | 整數欄含 NaN 會被升格成 float64 |
| **分箱與分類重組** | 連續值離散化、稀疏類別合併 | 等寬／等頻／K-Means 分箱；小類別併為 Other | 切分點沒依分佈設計 → 資訊損失、邊界偏誤 |
| **編碼轉換** | 類別變數轉為數值 | Label／Ordinal、One-Hot、Target Encoding | 虛假順序、維度爆炸、目標洩漏 |
| **標準化與正規化** | 消除量尺差異 | Min-Max、Z-score、Robust Scaling | 對離群值的抵抗力完全不同 |

### 型別轉換：pandas 的兩個經典坑

```python
# 坑 1：整數欄位只要含一個 NaN，pandas 就會把整欄升格成 float64
#       （NaN 本身是浮點數）→ 年份會顯示成 2006.0
#       注意：這不是「pandas 一律把數值讀成 float64」，純整數欄預設仍是 int64

# 坑 2：含 NaN 時直接轉 int 會報錯；用 fillna(0) 補又會扭曲分佈
df['Year'].astype(int)                     # 報錯：無法轉換 NaN
df['Year'].fillna(0).astype(int)           # 跑得動，但 0 年份會汙染趨勢分析
df['Year'] = df['Year'].astype('Int64')    # 正解：大寫 I 的可空整數型別
```

`'Int64'`（大寫）是 pandas 的 **nullable integer**，同時保留整數型態與缺值；`int64`（小寫）是 NumPy 型別，不接受 NaN。114-2 直接考過這一組。

### 分箱（Binning）＝ 特徵離散化（Feature Discretization）

| 方法 | 切法 | 適用 |
|---|---|---|
| **等寬（Equal-width）** | 數值範圍等距切（0–100 切 5 段，每段寬 20） | 分佈接近均勻；偏態資料容易出現空箱 |
| **等頻（Equal-frequency／Quantile）** | 每箱樣本數相近（如四分位） | 偏態資料、需要穩定樣本數 |
| **K-Means 分箱** | 用分群結果決定切點 | 資料有明顯群聚結構 |

把 UNIX 時間戳記轉成「早晨／下午／夜晚」這種操作，**最精確的名稱是特徵離散化（又稱分箱）**，不是 One-Hot，也不是降維 —— 115-1 考的就是這個用詞的精確度。

### 編碼：選錯的代價取決於下游模型

| 編碼 | 做法 | 適用 | 風險 |
|---|---|---|---|
| **Label / Ordinal Encoding** | 每個類別給一個整數 | **有序**類別（教育程度、Basic/Premium/VIP、滿意度 5 級） | 用在無序類別 → 線性與距離模型讀出虛假順序與虛假間距 |
| **One-Hot Encoding** | 每個類別一個 0/1 欄位 | **無序**類別、類別數不多 | 高基數（High Cardinality）→ 維度爆炸；線性模型要 `drop_first` 避免虛擬變數陷阱 |
| **Target Encoding** | 以該類別在目標變數上的統計量取代 | 高基數且與目標高度相關 | **目標洩漏**；必須只用訓練折計算 |

**「樹模型到底受不受編碼影響？」官方兩次考出看似相反的答案，前提要講清楚：**

```
樹只用「是否大於門檻」切分
  → 對編碼數值的單調變換不敏感，比線性模型耐受得多
    （115-1 第 42 題：不准改 1/2/3 的編碼，就改用隨機森林）
  → 但單次切分只能沿編碼順序切成前後兩段，
    永遠切不出 {1,3} vs {2} 這種分組，
    因此需要更深的樹，特徵重要性也會被編碼順序影響
    （114-2 第 17 題：GBT 直接吃 Label Encoding 會造成特徵重要性偏誤）
  → 所以 XGBoost 才提供 enable_categorical，讓演算法自己找最佳分組
```

### 縮放：三選一的判準是「有沒有離群值」

| 方法 | 中心／尺度 | 輸出 | 對離群值 |
|---|---|---|---|
| **Min-Max Normalization** | min／max | 壓到 0～1 | **最敏感**，一個極端值就壓扁其餘資料 |
| **Z-score Standardization** | 平均數／標準差 | 平均 0、標準差 1（**不是 0～1**） | 仍敏感，μ 與 σ 都會被拉偏 |
| **Robust Scaling** | 中位數／四分位距（IQR） | 無固定範圍 | **最穩健**，偏態或含離群值首選 |

需要縮放的是距離型（KNN、SVM、K-Means）、梯度型（線性／邏輯迴歸、神經網路）與含正則化的模型（Lasso、Ridge）；樹模型不需要。

## 33.2 特徵工程：選擇、衍生、增強

### 特徵選擇三家族

| 家族 | 判準 | 代表方法 | 優點 | 限制 |
|---|---|---|---|---|
| **Filter（過濾法）** | 統計量，獨立於模型 | 皮爾森相關係數、卡方檢定、ANOVA | 快、不綁模型 | 看不到特徵間交互作用；相關係數只抓**線性**關係 |
| **Wrapper（包裝法）** | 模型表現（準確率、F1） | RFE、前向／後向選擇 | 考慮互動效果 | 計算成本高、易過擬合 |
| **Embedded（嵌入法）** | 訓練過程中內建 | 樹的特徵重要性、Lasso／Ridge | 建模同時完成篩選 | 需特定模型支援，受超參數影響 |

### 特徵衍生與聚合

| 類型 | 做法 | 例子 |
|---|---|---|
| **交互特徵** | 特徵間四則運算 | 消費頻率 × 平均消費金額 = 年度消費總額；銷售金額 ÷ 瀏覽次數 |
| **時間特徵** | 從時間欄位衍生 | 星期幾、是否假日、距上次購買天數（Recency） |
| **聚合特徵** | 群組統計 | 顧客近三個月平均交易額、產品月銷售排名 |

**三個名詞官方直接考過分辨**：用既有欄位「算出」新欄位是**特徵衍生**；從既有欄位「挑子集」是**特徵選擇**；對單一欄位做數學變換（取對數、縮放）是**特徵轉換**。

### 資料增強：依資料型態選手法

| 資料型態 | 方法 | 案例 |
|---|---|---|
| **圖像** | 翻轉、旋轉、裁剪、縮放、色彩變換 | 人臉辨識、醫學影像 |
| **文字** | 同義詞替換、隨機插入／刪除／交換 | 情感分析、主題分類 |
| **時序** | 加噪、局部縮放（Jittering）、視窗裁切 | 設備故障預測、股市趨勢 |
| **表格** | **SMOTE**（少數類特徵空間內插生成） | 詐欺偵測、疾病診斷 |

SMOTE 是**內插生成**新樣本，Random Oversampling 是**複製**既有樣本 —— 後者樣本完全重複，過擬合風險明顯較高，114-2 有兩題考在這個分界上。另外要注意：增強的價值來自「每個訓練回合看到不同變化」，若為了吞吐量而把樣本預先轉成固定特徵並快取重複使用，等於凍結多樣性，過擬合反而惡化。

### 流程順序：本節最高頻的失分點

```
❌ 全體資料 → SMOTE / 目標編碼 / 特徵篩選 / 縮放 → 切分訓練與測試
✅ 切分訓練與測試 → 只用「訓練集」fit 轉換器 → 套用（transform）到測試集
```

任何會「學習資料統計性質」的步驟（SMOTE 的鄰居、目標編碼的平均值、相關係數門檻、StandardScaler 的 μ／σ）如果在切分前做，測試集資訊就滲進建模流程，分數虛高而不可信。115-1 連考三題（第 10、11、32 題）都踩這條線。

## 33.3 分散式運算框架：本節主幹

### 四大框架對照

| 框架 | 處理模式 | 適用情境 | 優點 | 缺點 |
|---|---|---|---|---|
| **Apache Hadoop（MapReduce）** | 批次處理 | 離線大量作業、日誌彙總、歷史分析 | 成熟穩定、HDFS 容錯強、易水平擴充 | 速度慢，不適合即時 |
| **Apache Spark** | **記憶體內運算**；批次與互動式查詢，串流採**微批次** | 大規模快速批次、資料分析、ML 訓練（MLlib） | 速度快、函式庫豐富、社群大 | 記憶體需求高、運維中等複雜 |
| **Apache Flink** | **原生逐事件串流**，批次視為有界串流 | 高頻即時事件（風控、即時推薦、IoT） | 真即時、高吞吐、狀態管理一致性佳 | 生態系比 Spark 小、維運投入較多 |
| **Apache Beam** | 統一批次／串流的**程式模型** | 跨平台、多雲、混合架構 | 可移植，換 Runner 不改邏輯 | 抽象層高、需理解 Dataflow Model |

**Beam 本身不含執行引擎**：它定義的是管線寫法，實際運算要指定 Runner（Flink／Spark／Google Dataflow）。這是它「可移植性強」的來源，也是它唯一的定位。

### MapReduce vs Spark：快在哪裡

| 面向 | Hadoop MapReduce | Apache Spark |
|---|---|---|
| **中間結果** | 每階段寫回 HDFS（**磁碟**） | 留在**記憶體**，可 `cache()`／`persist()` |
| **運算抽象** | Map → Shuffle → Reduce 固定兩段 | RDD／DataFrame 上的任意轉換鏈 |
| **排程** | 一個 Job 一組 Map/Reduce，多步驟要串多個 Job | **DAG（有向無環圖）排程器**，跨多步合併最佳化 |
| **求值時機** | 提交即執行 | **惰性求值（Lazy Evaluation）** |
| **容錯機制** | 失敗的 Task 重跑 + HDFS 多副本 | **Lineage（血統）** 記錄轉換來源，遺失分區就地重算 |
| **串流支援** | 無 | Structured Streaming（微批次） |

```
RDD（Resilient Distributed Dataset，彈性分散式資料集）三個必考性質
  ├─ 不可變（Immutable）：任何轉換都產生新的 RDD，不改動原本的
  ├─ 分區（Partitioned）：切成多個分區分散在各 Executor 上平行處理
  └─ 可重算（Lineage）：記住「我是從哪個 RDD 經哪些轉換來的」，
                        分區掉了就照血統重算，不必把中間結果全部落盤

惰性求值：Transformation vs Action
  Transformation（map / filter / select / join / groupBy）
    → 只是往 DAG 上加一個節點，實際什麼都還沒算
  Action（count / collect / take / show / write / reduce）
    → 才真正觸發整條 DAG 送去執行
  好處：引擎能在執行前把多個 filter、select 合併，少掃一次資料
```

### 批次 vs 微批次 vs 原生串流

| 面向 | 批次（Batch） | 微批次（Micro-batch） | 原生串流（Native Streaming） |
|---|---|---|---|
| **代表** | MapReduce、Spark 批次作業 | Spark Streaming／Structured Streaming | Flink、Kafka Streams |
| **觸發方式** | 定時（每日／每小時） | 每隔一小段時間收一批 | 事件一到就處理 |
| **延遲量級** | 分鐘～小時 | 通常秒級 | 毫秒～次秒級 |
| **吞吐 vs 延遲** | 吞吐最佳、延遲最差 | 折衷 | 延遲最佳 |
| **題幹關鍵字** | 「每日報表」「歷史回溯」 | 「近即時儀表板」 | 「毫秒級回應」「即時攔截」 |

### 串流生態裡誰負責什麼

| 元件 | 角色 | 常見誤解 |
|---|---|---|
| **Kafka** | 事件串流的**傳輸與儲存層**（訊息代理、可重播的事件日誌） | 以為 Kafka 自己做複雜分析；典型架構是 Kafka 後面接處理引擎 |
| **Flink／Spark Streaming** | **運算層**，做聚合、視窗運算、異常偵測 | 以為有 Kafka 就不必再選運算引擎 |
| **MQTT Broker** | IoT 裝置端的輕量訊息協定 | 不等於串流運算能力 |
| **資料湖／資料倉儲** | **落地層**，保存完整資料供訓練與回溯 | 以為它能提供即時性 |
| **Airflow／Prefect** | **編排層**，負責排程、相依與監控 | 以為它是運算引擎 |

### 平行化與分散式運算

```
垂直擴充（Scale-up）      加大單機 CPU／記憶體 → 有物理上限、成本非線性
水平擴充（Scale-out）     加節點 → 分散式框架的基本假設

資料平行（Data Parallelism）   同一段邏輯套到不同資料分區（Spark 的主要模式）
任務平行（Task Parallelism）   不同任務同時跑（Airflow DAG 上的分支）

分散式的主要成本在 Shuffle：跨節點搬資料
  ├─ 窄依賴（map / filter）：分區各算各的，不必搬資料 → 便宜
  └─ 寬依賴（groupBy / join / sortBy）：要跨分區重新分配 → 貴，且是 Stage 的邊界
資料傾斜（Data Skew）：某個 key 的資料量遠大於其他 key，
                       該分區變成長尾，拖垮整個 Job
```

**由此推得一條規則**：分散式環境要算全域統計量，做法是「各 Executor 先算局部統計量（筆數、總和、平方和），再彙總成全域結果」，而不是 `collect()` 把資料拉回 Driver 再用單機函式算 —— 115-1 第 21 題正是這一題。

## 33.4 Lambda vs Kappa 架構與資料管線

### 兩種混合架構

| 面向 | **Lambda 架構** | **Kappa 架構** |
|---|---|---|
| **組成** | 批次層（Batch Layer）＋ 速度層（Speed Layer）＋ 服務層（Serving Layer） | **只有串流層**＋ 服務層 |
| **歷史資料怎麼算** | 批次層定期全量重算，產出準確結果 | **重播（Replay）事件日誌**，用同一套串流程式重算 |
| **即時結果** | 速度層先給近似值，等批次層追上後被取代 | 串流層直接產出 |
| **程式碼** | **兩套**（批次一套、串流一套），邏輯要人工保持一致 | **一套** |
| **主要代價** | 維護成本高、兩層結果可能不一致 | 重播成本高，依賴可長期保存且可重播的日誌（如 Kafka） |

官方指引用的詞是「混合資料管線（Hybrid Pipeline）」—— 批次與即時並行，適用於「即時儀表板 ＋ 歷史回溯分析」這種複合需求，概念上就是 Lambda。

```
IoT 情境題的標準答案形狀（114-2 第 19 題）
  感測器 → 邊緣運算節點 → 串流處理框架 → 雲端資料湖 → 模型推論／再訓練
           ↑ 降低延遲      ↑ 即時偵測      ↑ 保留完整原始資料
  三個需求要同時滿足：毫秒級即時性、資料完整性、可擴展性
  只要流程主幹出現「批次特徵工程」或「雲端報表系統」，即時性就不成立
```

### 管線設計四原則

| 原則 | 意思 | 落地手段 |
|---|---|---|
| **可重現性（Reproducibility）** | 同樣輸入每次跑出同樣結果 | 版本控制、容器化 |
| **容錯與回復（Fault Tolerance & Recovery）** | 任務失敗能自動重試並告警 | 重試策略、冪等任務設計 |
| **擴充性與彈性（Scalability & Flexibility）** | 資料量或任務變多能加節點 | 任務模組化、無狀態設計 |
| **監控與可觀測性（Observability）** | 看得到當下與歷史執行狀態 | Grafana／Prometheus ＋ Slack／Email 告警 |

### 管線工具對照

| 工具 | 特點 | 適用 | 弱點 |
|---|---|---|---|
| **Apache Airflow** | Python 撰寫 DAG，Operator 與排程功能豐富 | 大規模、相依複雜的多任務管線 | 部署與維運相對複雜 |
| **Luigi** | Spotify 開源，架構清晰輕量 | 中小型任務、流程單純 | 功能單純、監控與圖形介面較弱 |
| **Prefect** | 現代化設計，容錯與監控強、UI 友善 | 追求操作簡便的資料科學團隊 | 功能不及 Airflow 廣，完整功能需雲端服務 |
| **Kubeflow Pipelines** | 以 Kubernetes 為基礎，專注 ML／AI 訓練流程 | 以機器學習為主的團隊、容器環境 | 安裝設定複雜、學習曲線陡 |

自動化建構要點的順序：**任務拆解與模組化** → **版本控管與 CI/CD 整合**（Git、GitHub Actions、Jenkins）→ **監控與警示設計** → **容器化與彈性擴充**（Docker、Kubernetes）。

多個團隊都要同一份行為資料時，導入統一管理與共用特徵（特徵平台）的**主要目的是消除跨團隊重複開發、降低維護成本並確保特徵定義一致**，不是解決推論延遲、儲存空間或模型版本管理 —— 後三者分屬服務架構、基礎設施與模型註冊表的範疇，115-1 第 31 題就拿它們當誘答。

## 33.5 pandas 與 scikit-learn：官方真的考語法

```python
# 1. 分組彙總：先 sum 再取前 N，順序不能反
df.groupby('CustomerID')['Revenue'].sum().nlargest(3)
#   .max()        → 每位客戶的「單筆」最高消費，不是總額
#   .head(3)      → 依 CustomerID 索引順序取前三個客戶，與金額高低無關
#   sort_values() → 排的是「單筆訂單」，靠多筆中型訂單累積的大客戶會落選

# 2. 條件篩選：布林遮罩要在中括號「外面」比較
df[df['Category'] == 'Electronics']['Revenue'].mean()
#   df['Category' == 'Electronics']  → 兩個字串常數相比，結果永遠 False
#   df.loc['Electronics', 'Revenue'] → loc 第一軸是列索引，未 set_index 會 KeyError
#   df.filter(items=[...])           → 篩的是「欄位名稱」，不是欄位內的值

# 3. 表格合併：how 決定保留誰
pd.merge(df, customers, on='CustomerID', how='inner')
#   inner 交集｜left 保留左表全部｜right 保留右表全部｜outer 聯集
#   pd.concat([df, customers], axis=1) → 依位置硬並排，完全不比對鍵值
#   df.join(customers, on='CustomerID') → 預設對右表的 index，且是 left join

# 4. 樞紐與長寬轉換
pd.melt(df, value_vars=['NA_Sales', 'EU_Sales'])       # 寬 → 長
df.pivot_table(index='Region', columns='Category',
               values='Revenue', aggfunc='sum')         # 長 → 寬，會聚合
#   df.pivot() 不做聚合，index/columns 組合重複就報錯

# 5. 記憶體不夠：分批讀，不是少讀
for chunk in pd.read_csv('big.csv', chunksize=100_000):
    process(chunk)
#   nrows=10000 → 只讀前 N 筆，等於丟掉絕大部分資料
#   dtype=...   → 能等比例壓低佔用，是輔助手段；50GB 打折後仍塞不進記憶體

# 6. apply 的軸向（用程式碼把話講死）
df.apply(f, axis=0)   # f 每次收到「一個欄（column）」，沿 index 方向運算（預設）
df.apply(f, axis=1)   # f 每次收到「一列（row）」

# 7. agg 回傳每組一列，transform 回傳與原資料等長
df.groupby('Region')['Revenue'].agg('mean')            # 每個 Region 一列
df['region_avg'] = df.groupby('Region')['Revenue'].transform('mean')   # 可直接指派回原表

# 8. scikit-learn 轉換器的 fit / transform 分工
scaler = StandardScaler()
X_train_s = scaler.fit_transform(X_train)   # 從訓練集學 μ、σ 並轉換
X_test_s  = scaler.transform(X_test)        # 測試集只 transform，不可再 fit
#   未 fit 就呼叫 transform → NotFittedError
#   scaler.fit(X) 的回傳值是 scaler 物件本身，不是轉換後的陣列
```

## 33.7 易錯與陷阱

- [ ] **Z-score 標準化是「平均 0、標準差 1」，不是「壓到 0～1」** —— 把範圍壓到 [0,1] 的是 Min-Max 正規化；官方刻意把這兩句寫進同一個選項當誘答。
- [ ] **Robust Scaling 用的是中位數與四分位距（IQR），不是平均數與標準差** —— 所以它抗離群值；Min-Max 與 Z-score 的參數都會被極端值污染。
- [ ] **Label Encoding 的主要風險是虛假順序，不是記憶體佔用過高** —— 它只用一個整數欄，記憶體反而最省；會維度爆炸的是 One-Hot。
- [ ] **樹模型是「對編碼數值的單調變換不敏感」，不是「完全不受編碼影響」** —— 單次切分只能沿編碼順序切成前後兩段，切不出 {1,3} vs {2}，所以 XGBoost 才要 `enable_categorical`。
- [ ] **分箱／特徵離散化是把連續值切成區間，不是 One-Hot 編碼** —— One-Hot 是離散化之後「可以再接」的下一步，而且展開後會丟掉區間之間的順序。
- [ ] **特徵衍生是用既有欄位算出新欄位，不是特徵選擇，也不是特徵轉換** —— 選擇是挑子集，轉換是對單一欄位做數學變換。
- [ ] **SMOTE 是在少數類特徵空間內插生成，不是複製既有樣本** —— 複製的是 Random Oversampling，那一個的過擬合風險才最高。
- [ ] **SMOTE、目標編碼、特徵篩選與 Scaler 都必須「先切分、只用訓練集 fit」，不是「先做完再切分」** —— 順序顛倒就是資料洩漏，測試分數會虛高到不可信。
- [ ] **Spark 快是因為中間結果留在記憶體、用 DAG 合併階段，不是演算法比 MapReduce 聰明** —— 記憶體不足時 Spark 一樣會溢寫到磁碟，速度優勢隨之縮小。
- [ ] **RDD 的容錯靠 Lineage 重算遺失分區，不是靠把每個中間結果都寫多份到磁碟** —— 寫多副本的是 HDFS 儲存層的機制。
- [ ] **Transformation（map／filter／join）是惰性的、只在 DAG 上加節點，不會立刻執行** —— 真正觸發運算的是 Action（count／collect／show／write）。
- [ ] **Flink 是原生逐事件串流、把批次視為有界串流，不是把串流切成微批次** —— 微批次是 Spark Streaming 的做法，延遲量級通常在秒級。
- [ ] **Kafka 是事件的傳輸與可重播儲存層，在典型考題架構中不是運算引擎** —— 即時聚合與異常偵測要靠後面接的 Flink／Spark Streaming（Kafka Streams 是同生態的函式庫，屬例外而非題目預設）。
- [ ] **Lambda 架構是批次層與速度層並存、維護兩套邏輯，Kappa 才是只留串流層** —— Kappa 靠重播事件日誌補算歷史，換來一套程式碼，但重播成本高。
- [ ] **Apache Beam 是統一的程式模型，本身不含執行引擎** —— 實際運算要指定 Runner（Flink／Spark／Dataflow），可移植性正是它的賣點。
- [ ] **分散式算全域統計要「各節點先算局部、再彙總」，不是 `collect()` 回 Driver 再用單機函式** —— 10 億筆拉回單一節點會 OOM，也放棄了叢集的平行能力。
- [ ] **Airflow／Prefect 是編排與排程工具，不是運算引擎** —— 它負責觸發、相依與監控，實際運算仍交給 Spark、SQL 或 Python 任務。
- [ ] **讀不下大檔要用 `chunksize` 分批，不是 `nrows`** —— `nrows` 只讀前 N 筆等於丟資料；`dtype` 只能等比例壓縮，是輔助不是解法。
- [ ] **`pd.merge(how='inner')` 取交集、`how='outer'` 取聯集，而 `pd.concat(axis=1)` 完全不比對鍵值** —— `df.join` 預設對的是右表的 index 且為 left join。
- [ ] **整數欄含 NaN 會被 pandas 升格成 float64，不是「pandas 一律把數值讀成 float64」** —— 要同時保留整數與缺值，用 `astype('Int64')`（大寫 I）。
- [ ] **`groupby().agg()` 每組回傳一列，`groupby().transform()` 回傳與原資料等長** —— 想把組統計量指派回原表當新欄位，要用 `transform`。
