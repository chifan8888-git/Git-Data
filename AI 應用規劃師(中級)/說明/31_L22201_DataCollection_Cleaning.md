# 31. L22201 數據收集與清理（45 分鐘）

> 一句話定位：初級的 L112 把「補缺失值、去重複」當成單機一張 CSV 的小手術；中級 L22 的切角是**大數據規模**—— 資料從感測器、API、爬蟲、日誌四面八方湧進來，型態異質、更新頻繁、量體超過單機記憶體，你要決定的是**用什麼管道收、用什麼節奏收、髒在哪一層、以及在這個量級下哪一種清理手段還跑得動**。

## 學習目標
- 依資料型態（結構化／半結構化／非結構化）與更新頻率，選出對應的蒐集管道與技術組合
- 辨識五大類資料品質問題，並用量化的資料品質指標定位問題欄位
- 依缺失機制與分布形狀，從刪除／統計量填補／插補／模型預測／保留中選出正確手段並說出其副作用
- 在記憶體不足、資料跨節點的情境下，指出可行的讀取與清理工程作法

## 31.1 資料來源型態與蒐集方式

### 五類來源對照

| 來源 | 資料型態 | 典型蒐集方式 | 主要挑戰 |
|---|---|---|---|
| **感測器與物聯網（IoT）** | 結構化時間序列，高頻連續 | MQTT、Apache Kafka 串流；邊緣運算（Edge Computing）就近預處理 | 高併發、低延遲、斷訊造成**連續缺失** |
| **系統日誌／使用者行為** | 半結構化或非結構化 | Flume、Logstash 批次傳輸；Apache NiFi 即時管線；落地至 HDFS、Elasticsearch | 各系統日誌**格式不一致**；高頻日誌的儲存壓力 |
| **API 與外部資料交換** | 半結構化（JSON／XML） | RESTful API 程式化請求，搭配 Airflow、Talend 做 ETL | **速率限制（Rate Limit）**、認證、分頁；欄位結構改版需動態調整解析 |
| **網路爬蟲／開放資料** | 結構化或半結構化 | Scrapy、BeautifulSoup 自動擷取；開放平台（data.gov、Kaggle）下載 | 反爬機制、robots.txt 與法遵；**開放資料集品質參差** |
| **企業內部營運系統（ERP／CRM／POS）** | 結構化 | SQL 查詢、CSV 批次匯出、資料倉儲整合（BigQuery、Snowflake） | 跨部門**命名與格式不一**；歷史資料遺漏 |

### 選擇蒐集策略的五個關鍵因素

官方指引明列這五項，情境題幾乎都是在其中兩三項之間權衡：

```
更新頻率 → 即時串流，還是定期批次？
格式轉換 → 非結構化要不要先解析成結構化？解析在邊緣做還是雲端做？
即時性   → 有沒有低延遲需求（即時推薦、毫秒級告警）？
資料品質 → 完整性、一致性、準確性由誰把關？在入湖前還是入湖後？
隱私合規 → GDPR、CCPA、個資法；去識別化要在哪一層做？
```

## 31.2 蒐集模式：批次、串流與混合架構

### 批次 vs 串流

| 維度 | 批次處理（Batch） | 串流處理（Streaming） |
|---|---|---|
| **觸發** | 排程（每日／每小時） | 事件到達即處理 |
| **延遲** | 分鐘到小時級 | 毫秒到秒級 |
| **資料範圍** | 有界（Bounded），可完整重算 | 無界（Unbounded），只看得到目前視窗 |
| **代表工具** | Spark、Hive、Airflow 排程 | Kafka、Flink、Spark Structured Streaming |
| **典型題目** | 月報表、模型重訓 | IoT 異常告警、即時推薦、詐欺攔截 |
| **清理特性** | 可做全域統計（全欄位中位數、重複值全比對） | 只能做視窗內統計與規則式檢核 |

**這個差異決定了清理手段能不能用。** 全域去重、全欄位分位數這類需要看完整份資料的動作，在串流層做不到，只能在批次層或落地後補做 —— 這正是混合架構存在的理由。

### 混合架構

```
Lambda 架構
  ├─ 速度層（Speed Layer）：串流處理，追求低延遲，結果可能近似
  ├─ 批次層（Batch Layer）：保留完整原始資料，定期重算出精確結果
  └─ 服務層（Serving Layer）：合併兩者供查詢
  代價：同一套邏輯要寫兩份（串流一份、批次一份）

Kappa 架構
  └─ 只留串流一條路徑，需要重算就把訊息重播（Replay）一次
     前提：訊息佇列本身可持久化並支援重播（Kafka 的 log 即可）
```

官方 114Q2-19 考的正是這個骨架：上萬台感測器、毫秒級回應、同時要保留完整資料供訓練 —— 正解是「感測器 → **邊緣運算節點** → **流式處理框架** → **雲端資料湖** → 模型推論」。邊緣負責降延遲、串流負責即時分析、資料湖負責完整留存，三個需求各有對應的一段。

### MQTT 與 Kafka 不是同一層的東西

| | MQTT | Apache Kafka |
|---|---|---|
| **定位** | 輕量發佈／訂閱**訊息協定** | 分散式**串流平台／持久化日誌** |
| **設計場景** | 低頻寬、不穩定網路、電力受限的裝置端 | 資料中心內高吞吐匯流與重播 |
| **訊息保留** | 通常不長期保留 | 依保留策略持久化，可重播 |
| **實務組合** | 裝置 → MQTT Broker → **橋接進 Kafka** → 串流處理 | |

### ETL 與 ELT

- **ETL**：Extract → **Transform** → Load。轉換完才進目的地，適合綱要固定的資料倉儲（schema-on-write）。
- **ELT**：Extract → Load → **Transform**。先把原始資料丟進資料湖，查詢時才套綱要（schema-on-read）。大數據與雲端環境多採此法，因為異質、半結構化資料在入湖前往往還來不及定義綱要。

## 31.3 資料品質問題的五大類型

| 類型 | 定義 | 大數據情境下的典型成因 | 影響 |
|---|---|---|---|
| **缺失值（Missing Data）** | 欄位無值（NaN／NULL／空字串） | 感測器斷線、使用者跳答、傳輸中斷、API 回傳欄位缺漏 | 樣本偏差；線性模型無法直接處理空值 |
| **異常值／離群值（Outliers）** | 偏離資料主體分布的極端值 | 輸入錯誤、設備故障、單位錯置，**或真實罕見事件** | 扭曲平均數與標準差，影響檢定與迴歸顯著性 |
| **重複值（Duplicates）** | 同一觀察單位重複出現 | 多來源整合、重試機制重複寫入、缺少唯一識別碼 | 高估頻次與總量；**可能造成資料洩漏** |
| **一致性錯誤（Inconsistency）** | 單位、格式、命名不統一 | 跨系統整合、人工輸入 | 無法正確聚合與比對；拉高清理成本 |
| **邏輯錯誤（Logical Errors）** | 格式合法但違反領域知識 | 缺少規則檢核 | 模型失效、推論錯誤，且**不會被型別檢查攔到** |

**一致性錯誤的實例**：「臺北市」與「台北市」、`2023/01/01` 與 `Jan-1-2023`、公斤與磅混用、UTF-8 與 Big5 編碼混雜、時區未標準化。

**邏輯錯誤的實例**：出生年 1890、交易金額為負（除非是退貨）、體溫 43°C、訂單結束時間早於開始時間。

> 分辨關鍵：**一致性錯誤是「同一件事有多種寫法」，邏輯錯誤是「寫法沒問題但值不可能成立」。** 前者靠標準化規則解決，後者要靠領域專家訂出範圍與跨欄位規則（年齡 0–120、金額 ≥ 0、end ≥ start）。

## 31.4 缺失值處理：機制判斷與方法選擇

### 先判斷缺失機制

| 機制 | 判準 | 例 | 對處理的意義 |
|---|---|---|---|
| **MCAR**（完全隨機缺失） | 缺失與任何變數（含自己）皆無關 | 傳輸偶發丟包造成的隨機跳漏 | 直接刪除列**幾乎不產生偏誤** |
| **MAR**（隨機缺失） | 缺失機率可由其他**已觀測**欄位解釋 | 年輕族群較少填「年收入」，而年齡欄完整 | 可用其他欄位做模型填補（KNN、MICE） |
| **MNAR**（非隨機缺失） | 缺失機率取決於該欄位**自己未觀測到的值** | 收入越高越不願填收入；重症者拒答健康題 | 刪除會引入選擇偏誤；**缺失本身是訊號**，應加缺失指標欄 |

> 官方《學習指引》以「高收入者較不填寫」示例 MAR、以「特定族群不回應」示例 MNAR。在嚴格統計定義下，若缺失只與收入本身有關，該例其實落在 MNAR。**考試時抓一句判準就夠：缺失原因能不能由資料中其他已觀測欄位說明？** 能 → MAR；說明不了且與自身值有關 → MNAR；與任何變數都無關 → MCAR。

### 處理方法適用時機對照表（本節重點）

| 方法 | 作法 | 最適用時機 | 副作用／風險 |
|---|---|---|---|
| **整列刪除** | `dropna()` | 缺失率低（經驗上 < 5%）**且**接近 MCAR、樣本充裕 | MNAR 下產生選擇偏誤；高缺失率會大量損失樣本 |
| **整欄刪除** | `drop(columns=...)` | 該欄缺失率極高且無替代資訊來源 | 可能丟掉有預測力的欄位；缺失樣態本身可能有訊息 |
| **平均數填補** | `fillna(mean)` | 數值欄、分布**近似對稱**、無明顯離群值 | **低估變異數**、壓縮相關係數；偏態資料會整體位移 |
| **中位數填補** | `fillna(median)` | 數值欄、**右偏或含離群值**（mean 明顯大於 median） | 同樣壓縮變異；無法反映個體差異 |
| **眾數填補** | `fillna(mode)` | 類別型／離散欄位 | 強化多數類別、稀釋少數類別 |
| **固定值／哨兵值** | `fillna(-1)`、`"Unknown"` | 樹模型；缺失本身有意義且需明確標記 | 對線性與距離型模型是災難，等於灌入假數值 |
| **前向／後向填補** | `ffill` / `bfill` | 時間序列短暫斷訊；**`ffill` 只用過去資訊** | 長段缺失會產生一條假的水平線；`bfill` 帶前瞻偏誤 |
| **線性／時間插值** | `interpolate()` | 連續且變化平滑的**短**缺口 | 需用到缺口**之後**的觀測值；長缺口會捏造不存在的趨勢 |
| **模型預測填補** | KNN Imputer、迴歸、MICE 多重插補 | 欄位間相關性強、缺失率中等、算力足夠 | 成本高；**必須只用訓練集擬合**，否則資料洩漏 |
| **保留缺失** | 交給原生支援的演算法 | XGBoost、LightGBM 可在分裂時學一個預設方向 | 換模型就得重做；統計檢定仍須自行處理 |
| **加缺失指標欄** | `df['x_isna'] = df['x'].isna()` | 疑似 MNAR、缺失與目標有關 | 增加維度，須與其他填補法搭配使用 |

> 官方指引提到「保留缺失、交給可處理缺失值的演算法（如隨機森林）」。實務上是否真的免填補要看套件實作：XGBoost、LightGBM 原生支援，scikit-learn 的部分估計器則會直接拋錯，不能一概而論。

### 選哪一個：一條判斷線

```
缺失率 > 50~70%？ ──YES→ 考慮整欄刪除（先確認缺失樣態是否有訊息）
        │NO
缺失率 < 5% 且判定接近 MCAR？ ──YES→ 整列刪除
        │NO
是時間序列？ ──YES→ ffill（即時情境首選）／短缺口用插值；長缺口整段捨棄
        │NO
欄位是類別型？ ──YES→ 眾數或 "Unknown"
        │NO
分布右偏或有離群值（mean 明顯大於 median）？ ──YES→ 中位數
        │NO
與其他欄位高度相關且算力允許？ ──YES→ KNN／MICE
        │NO
        └→ 平均數（基線做法），並評估變異數被壓縮的影響
```

官方 115Q1-41 就是照這條線走的：`describe()` 顯示 mean 223.41、median 128.55、max 4500，明顯右偏長尾，缺失率 5% —— 正解是**中位數填補**。用平均數會把大量補值灌到遠高於典型水準的位置、用最大值等於憑空製造離群值、直接刪掉 5% 則損失樣本且可能引入選擇偏誤。

## 31.5 離群值、重複值與一致性錯誤的處理

### 離群值偵測方法對照

| 方法 | 判準 | 分布假設 | 適用情境 |
|---|---|---|---|
| **Z 分數（Z-Score）** | `Z = (x − μ) / σ`，以 \|Z\| ≥ 3（有時用 2）為門檻 | 近似常態、單變量 | 對稱分布、樣本量大 |
| **IQR／箱型圖法** | 低於 `Q1 − 1.5×IQR` 或高於 `Q3 + 1.5×IQR` | 無分布假設、單變量 | 偏態資料比 Z 分數穩健 |
| **修正 Z 分數（MAD）** | 以中位數與中位數絕對偏差取代 μ 與 σ | 穩健統計 | 小樣本、已知含極端值 |
| **孤立森林（Isolation Forest）** | 隨機切分下被「孤立」所需的深度 | 多變量、無分布假設 | 高維、大資料量 |
| **LOF／DBSCAN** | 局部密度 | 多變量 | 群集型異常；**維度過高會全面失效** |

**Z 分數與 IQR 互為誘答**：Z 分數用的 μ 與 σ 本身就會被離群值污染（幾個極端值同時拉高平均與標準差，反而讓 |Z| 變小），所以偏態或極端值多的資料改用 IQR 或 MAD 較可靠。

### 偵測到之後怎麼處理

```
先問一句：這是「錯誤」還是「真實但罕見」？
  輸入／單位錯誤  → 修正，修不了就移除
  設備故障        → 移除該時段，並標記感測器狀態
  真實罕見事件    → 保留！詐欺、設備異常、高消費族群，
                    這些離群值往往就是建模的目標本身
  不確定          → 蓋帽（Winsorizing，壓到 1%／99% 分位數）
                    或取對數壓縮長尾，而不是直接刪掉
```

114Q2-25 的誘答就設在這裡：箱型圖 IQR 很小、上鬚拉得很長、高金額區多筆離群值，選項「移除所有離群值讓資料集中」是錯的 —— 高消費族群正是行銷分群要找的層級，正解是**改用對數刻度**呈現。

### 重複值

| 型態 | 偵測 | 處理 |
|---|---|---|
| **完全重複**（整列相同） | `df.duplicated()` | `drop_duplicates(keep='first' 或 'last')` |
| **主鍵重複**（ID 相同、內容不同） | `duplicated(subset=['id'])`；監控唯一值比率 | 依時間戳記保留最新，或整合欄位後再去重 |
| **實體重複**（同一對象多筆，無共同 ID） | 模糊比對／實體解析（姓名＋電話＋地址組合鍵） | 建立主資料（Master Data）後映射 |

重複值除了高估頻次與總量、破壞卡方檢定的頻次分布外，在建模流程還有一個更隱蔽的殺傷力：**同一筆記錄的複本被切分到訓練集與測試集兩邊，測試分數會被高估**。

### 一致性錯誤的標準化順序

```
1. 編碼統一（全部轉 UTF-8）
2. 去除前後空白、全形／半形正規化
3. 日期時間統一為 YYYY-MM-DD（含時區）
4. 單位統一（公斤／磅、新台幣／美元，並在欄名標註單位）
5. 類別值對映到受控詞彙表（臺北市／台北市／TPE → 臺北市）
6. 最後才做邏輯規則檢核（範圍、跨欄位關係）
```

## 31.6 資料品質指標與大規模清理工程

### 五個量化指標

| 指標 | 衡量什麼 | 層級 | 異常時代表 |
|---|---|---|---|
| **缺失率（Missing Rate）** | 單一欄位中空值的比例 | **欄位**層級 | 蒐集流程異常，或該欄不適合用於分析 |
| **唯一值比率（Uniqueness Rate）** | 主鍵／識別碼的重複情形 | 欄位層級 | 主鍵重複會直接破壞資料正確性 |
| **一致性比率（Consistency Rate）** | 格式、單位、命名是否統一 | 欄位層級 | 解析困難，不利資料共享與再利用 |
| **異常值比率（Outlier Rate）** | 偏離正常分布的數值比例 | 欄位層級 | 輸入錯誤、轉碼問題，或真實罕見行為 |
| **完整性比率（Completeness Rate）** | 一個觀察對象是否具備足夠欄位來描述 | **記錄／實體**層級 | 個人資料有、行為紀錄缺 → 限制模型應用 |

> **缺失率與完整性比率不是同義詞**：前者問「這一欄有多少格是空的」，後者問「這一筆對象該有的資料齊不齊」。兩者層級不同，可能同時出現「每欄缺失率都很低，但完整記錄比率很差」的情況。

這些指標的價值在於可以內嵌進資料管線（Data Pipeline）做**自動化偵測與告警**，而不是只在專案初期人工檢查一次。模型上線後的輸入特徵監控是同一套邏輯 —— 115Q1-5 就是用 `|Z| ≥ 2` 當門檻監控特徵漂移（Data Drift）。

### 量體超過單機時的清理工程

| 情境 | 作法 | 為什麼 |
|---|---|---|
| 50GB CSV 遠大於記憶體 | `pd.read_csv(..., chunksize=N)` **分批讀取** | 回傳可迭代物件，記憶體用量與檔案總大小脫鉤 |
| 記憶體吃緊但塞得下 | 指定 `dtype`（int64→int32、字串→category）、`usecols` 只讀需要的欄 | 只是**等比例壓縮**，無法根治 |
| 資料已分散在叢集 | Spark `DataFrame.agg({'col':'stddev'})`、`RDD.aggregate()` | 各 Executor 先算局部統計量再彙總，只掃一次、傳輸量極小 |
| 多來源異質（文字＋影像＋表格） | 入**資料湖**，以 Spark／Ray 做分散式預處理再串接訓練管線 | 單節點批次處理會成為瓶頸 |
| 整數欄含 NaN | `astype('Int64')`（大寫 I，可空整數型態） | 保留整數型態同時容納缺失 |

```python
# 分批清理的骨架（read_csv 逐批讀入，原始檔不會一次進記憶體；下方 concat 則假設「清理後」的結果塞得下）
cleaned = []
for chunk in pd.read_csv("events_50gb.csv", chunksize=100_000,
                         dtype={"user_id": "int32", "channel": "category"}):
    chunk = chunk.drop_duplicates(subset=["event_id"])           # 批內去重
    chunk["ts"] = pd.to_datetime(chunk["ts"], errors="coerce")   # 無法解析→NaT
    chunk = chunk[chunk["amount"] >= 0]                          # 邏輯規則檢核
    cleaned.append(chunk)

df = pd.concat(cleaned, ignore_index=True)
df = df.drop_duplicates(subset=["event_id"])   # 跨批次去重必須在合併後再做一次
print(df.isna().sum())                          # isnull() 與 isna() 等價
```

> 注意最後的跨批去重：**批內去重無法處理「複本落在不同批次」的情況**，這是分批處理最常被忽略的破口。

## 31.8 易錯與陷阱

- [ ] **Z 分數的正負號代表方向** —— Z = −2 是「**低於**平均 2 個標準差」，不是高於；也不是「落在母體分布之外無法解釋」，|Z| = 2 約在雙尾 5% 的位置，常態分布完全描述得了。
- [ ] **|Z| 的大小與「是不是離群值」是兩件事** —— Z = 2 只說明偏離程度，判不判為離群值取決於**事先設定的門檻**（常用 3）；看到 Z = 2 就斷定為異常值是官方設過的誘答。
- [ ] **Z 分數用的 μ 與 σ 自己會被離群值污染** —— 極端值同時拉高平均與標準差，反而讓 |Z| 縮小；偏態或極端值多時該改用 **IQR 或 MAD**，不是硬套 Z 分數。
- [ ] **箱型圖的鬚線畫到「圍籬內最極端的實際觀測值」** —— 不是直接畫在 `Q1 − 1.5×IQR` 與 `Q3 + 1.5×IQR` 這兩個數值上；超出圍籬的點才單獨標成離群點。
- [ ] **右偏長尾要用中位數填補，不是平均數** —— 判斷訊號是 `describe()` 裡 mean 明顯大於 median；平均數已被極端值拉高，拿它補值會讓整個分布往高值端位移。
- [ ] **平均數填補會低估變異數** —— 所有補值都堆在中心，標準差與相關係數一起被壓縮；它不是「不影響分布」的中性做法。
- [ ] **「缺失率低就可以刪除列」要加上接近 MCAR 這個前提** —— 若缺失屬 MNAR（例如高收入者不填收入），刪掉的是特定族群，會引入選擇偏誤。
- [ ] **`ffill` 只用過去資訊，`interpolate` 會用到缺口之後的值** —— 在即時預測或時序驗證情境下，插值等於偷看未來；兩者不能互換。
- [ ] **感測器漂移是隨時間累積的系統性偏移** —— 要用滾動中位數或基準校正；對整段序列做 Z-score 標準化只是改變尺度、扣掉全域平均，漂移原封不動留在資料裡。
- [ ] **重複值的風險不只是高估總量** —— 同一筆記錄的複本分落訓練集與測試集，會讓測試分數失真；這是重複值造成的資料洩漏。
- [ ] **分批處理時，批內去重不等於全域去重** —— 複本若落在不同 chunk 就抓不到，必須在合併後再去重一次。
- [ ] **一致性錯誤是「同一件事多種寫法」，邏輯錯誤是「寫法合法但值不可能」** —— 前者用標準化規則解決（臺北市／台北市、kg／公斤），後者要靠領域規則檢核（出生年 1890、體溫 43°C）。
- [ ] **缺失率是欄位層級，完整性比率是記錄層級** —— 前者問「這一欄多少格是空的」，後者問「這一筆對象該有的資料齊不齊」，兩個指標不能互相代用。
- [ ] **pandas 的缺失值計數是 `isnull()` 或 `isna()`（兩者等價）** —— `isNaN()` 與 `isnan()` 不是 DataFrame 的方法，呼叫會拋 AttributeError。
- [ ] **整數欄被讀成 float64，主因是欄中含 NaN 或原值帶小數點** —— 不是「pandas 一律把數值讀成 float64」；含缺失又要整數，用 `astype('Int64')` 而不是 `fillna(0).astype(int)`。
- [ ] **`chunksize` 才是解 OOM 的根治手段** —— `dtype` 只是等比例壓縮（50GB 打對折仍塞不下）、`nrows` 是直接丟掉大部分資料，兩者都只能當輔助。
- [ ] **MQTT 是輕量傳輸協定，Kafka 是可持久化、可重播的串流平台** —— 兩者常串接使用（裝置 → MQTT Broker → 橋接 Kafka），不是互相取代的同層選項。
- [ ] **離群值不一定要刪** —— 詐欺交易、設備故障、高消費族群這類任務裡，離群值本身就是答案；「移除所有離群值以讓資料集中」是標準誘答。
- [ ] **Python 清洗函式別用可變物件當預設參數** —— `def f(rec, tags=[])` 的空 list 在**定義時只建立一次**，之後每次未傳入都共用同一個物件，不是每次呼叫都給一個新的空 list。
